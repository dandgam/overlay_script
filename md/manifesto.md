# Манифест разработки агентных систем и проектов на LLM

> Это не «best practices» в общем — это анти-патогены к конкретным failure modes,
> с которыми сталкиваешься, когда строишь систему, которая запускает другие системы.

## Как читать этот документ

Манифест разделён на **три уровня**, потому что правила разного веса не должны лежать в одном списке:

1. **Архитектурные принципы** — как устроена система в принципе. Меняются редко, при смене — переписывается всё.
2. **Дисциплина исполнения** — как ты пишешь и меняешь систему. Применяются на каждой сессии.
3. **Мета-правила** — как не сойти с ума и не построить мусор. Про работу с собой и с LLM.

Каждое правило сформулировано в формате:
- **Правило** — одно предложение
- **Обоснование** — почему это правило существует
- **Пример нарушения** — как выглядит, когда правило игнорируют
- **Критерий слома** — когда правило перестаёт работать и нужно остановиться

Без критерия слома любое правило превращается в догму, а догма в инженерии хуже отсутствия правила.

# Уровень 1. Архитектурные принципы

## A1. Скрипты для форм, LLM для смыслов

**Правило.** На каждом шаге пайплайна спроси: «это решение про форму или про смысл?» Форма → детерминированный скрипт. Смысл → LLM-judge. Никогда не наоборот.

**Обоснование.** LLM на форматных задачах — это деньги в трубу, недетерминизм там, где его быть не должно, и неотлаживаемые баги. Скрипт на семантических задачах — это длинные регулярки, которые ломаются на первом нестандартном входе.

**Пример нарушения.** Использовать LLM для парсинга JSON, извлечения email из строки, проверки длины поля, нормализации даты. Использовать regex для определения «это спам» или «это жалоба».

**Критерий слома.** Когда форма становится семантически нагруженной: например, «извлечь дату» из текста «через две недели после следующей пятницы» — это уже смысл, а не форма.

---

## A2. Состояние на диске, а не в разговоре

**Правило.** Каждый артефакт — файл. Каждый handoff между шагами — чтение файла, а не передача через контекст. Контекст разговора — это рабочая память, а не хранилище.

**Обоснование.** Состояние в контексте = невоспроизводимость, невозможность дебажить постфактум, потеря данных при сбое, невозможность параллелизации.

**Пример нарушения.** Шаг 1 «извлекает данные», шаг 2 «принимает их по контексту». Через неделю воспроизвести что произошло — невозможно.

**Критерий слома.** Когда размер артефакта становится больше разумного (гигабайты) — нужно переходить на специализированное хранилище (БД, object storage), но принцип «состояние снаружи разговора» остаётся.

---

## A3. Хуки про гарантии, промпты про вероятность

**Правило.** Если требование звучит как «гарантированно делает X» — это хук, валидатор, schema, post-condition в коде. Если «обычно делает X» — это промпт.

**Обоснование.** Промпт = «модель скорее всего сделает то, что просишь». Хук = «система либо сделает, либо остановится». Это разный класс утверждений и разная стоимость инцидента.

**Пример нарушения.** «В промпте написано — никогда не выдавать персональные данные» — и всё. Без выходного фильтра это не гарантия, а пожелание.

**Критерий слома.** Когда «гарантия» требует понимания смысла (например, «гарантированно не выдавать конфиденциальную информацию») — нужен LLM-judge как часть хука, а не вместо него.

---

## A4. Детерминизм на границе исполнения

**Правило.** Выход LLM, который попадает в исполняемый код, в состояние системы или во внешний мир (API, БД, email), должен пройти через детерминированный валидатор с **closed-set** допустимых форм. Не «парсить как получится», а «либо матчит схему, либо ошибка».

**Обоснование.** Стохастический выход на детерминированном входе = катастрофа. LLM, генерирующий SQL для прямого исполнения — классический пример анти-паттерна.

**Пример нарушения.** `eval(llm_output)`, `exec(llm_output)`, отправка `llm_output` напрямую в API без валидации.

**Критерий слома.** Когда множество допустимых форм действительно open-set (например, генерация произвольного кода для человека-ревьюера) — нужен другой защитный слой: human-in-the-loop или sandbox.

---

## A5. Иерархия: оркестратор-скрипт + узкоспециализированные LLM-воркеры

**Правило.** Оркестратор — это Python/Make/bash, а не LLM. Управление пайплайном, ветвление, retry, расписание — всё в коде. LLM появляются только на шагах, где нужен смысл. Узкая специализация: один воркер — одна задача.

**Обоснование.** «LLM-оркестратор, который запускает LLM-воркеров» — это система, которую невозможно отлаживать, в которой ошибки накапливаются и в которой ты платишь за токены за то, чтобы модель выбрала следующий шаг из трёх возможных.

**Пример нарушения.** Агент «решает», что делать дальше, на каждом шаге через промпт «вот что у нас есть, что делать?» — вместо явного state machine.

**Критерий слома.** Когда задача действительно требует динамического планирования с большой вариативностью (например, исследовательский агент), но и тогда план должен сначала генерироваться, потом валидироваться, потом исполняться оркестратором-скриптом.

# Уровень 2. Дисциплина исполнения

## B1. Enumeration перед имплементацией

**Правило.** Прежде чем писать скрипт на шаге пайплайна, перечисли все типы ситуаций списком (closed-set). Если таксономия не закрывается — это сигнал, что задача не подходит для скрипта.

**Обоснование.** «Сейчас напишу, по ходу разберусь» — это reactive-patch trap в зародыше. Через три месяца у тебя будет 40 if-ов, и никто не сможет сказать, что они покрывают.

**Пример нарушения.** Начать писать обработчик ошибок без списка ошибок. Начать классификатор без списка классов.

**Критерий слома.** Когда после N итераций таксономия не закрывается — нужно явно признать: «здесь нужен LLM-judge с fallback на hard-halt», а не растягивать enumeration бесконечно.

---

## B2. Один скрипт на семейство ситуаций, не на ситуацию

**Правило.** Новый случай мапится в существующую категорию таксономии или явно расширяет её. Не плодим скрипты на каждый частный случай.

**Обоснование.** N скриптов на N ситуаций = O(N) точек поддержки и O(N²) точек взаимодействия. Через полгода никто не помнит, какой скрипт что делает.

**Пример нарушения.** `handle_user_a.py`, `handle_user_b.py`, `handle_user_c_special.py`. Должен быть `handle_user.py` с явной таксономией внутри.

**Критерий слома.** Когда внутри одного скрипта становится >300 строк ветвления — таксономия выросла, пора декомпозировать на семейства.

---

## B3. Четыре уровня реакции на event, никогда detect-halt

**Правило.** На каждое событие в пайплайне реакция выбирается из четырёх уровней:
1. **try-fix** — система знает как починить и чинит
2. **soft-warn** — записываем в лог, продолжаем
3. **LLM-judge** — нужен смысловой разбор, зовём модель
4. **hard-halt** — exit, raise, зовём человека

Запрещено: **detect-halt** — увидеть проблему и просто остановиться без явного выбора уровня.

**Обоснование.** Detect-halt = молчаливая деградация. Система либо лечится, либо явно зовёт на помощь — других режимов быть не должно.

**Пример нарушения.** `if error: return` без логирования, без классификации, без эскалации.

**Критерий слома.** Когда try-fix начинает скрывать системную проблему (например, всегда успешно «чинит» одно и то же) — нужно поднимать на soft-warn или выше для анализа таксономии.

---

## B4. Schema-валидация артефактов на каждой границе

**Правило.** Каждый артефакт имеет явную схему. На входе шага — валидация. На выходе шага — валидация. Версия схемы — часть артефакта.

**Обоснование.** «Состояние на диске» работает только если состояние имеет известную форму. Иначе вчерашний LLM-воркер пишет в одной форме, сегодняшний — в другой, оркестратор молча сломан.

**Пример нарушения.** `state.json` без схемы, без версии. Через месяц после рефакторинга — старые артефакты не читаются, новые читаются неправильно, никто не знает.

**Критерий слома.** Когда схема становится узким местом (например, нужна обратная совместимость с N версиями) — переходить на явные миграции артефактов, но валидация остаётся.

---

## B5. Идемпотентность и явная retry-семантика

**Правило.** Каждый шаг либо идемпотентен (повторный запуск с тем же входом → тот же результат, без побочных эффектов), либо явно помечен как non-idempotent с описанием компенсирующего действия.

**Обоснование.** Пайплайны падают. Если шаг не идемпотентен и нет компенсации — перезапуск либо невозможен, либо опасен. Это часть «состояние на диске», но требует отдельной дисциплины.

**Пример нарушения.** Шаг «отправить письмо клиенту» без проверки «уже отправлено?». При retry клиент получает два письма.

**Критерий слома.** Когда идемпотентность стоит слишком дорого (например, генеративная задача с дорогими токенами) — нужно явное «кеширование результата как часть состояния», но это уже не отсутствие идемпотентности, а её эмуляция.

---

## B6. Audit trail и observability — это разные вещи, и нужны обе

**Правило.**
- **Audit trail** = «что произошло». `events.jsonl`, `decisions.log`, `state.json`. Используется постфактум.
- **Observability** = «что происходит прямо сейчас». Метрики, трейсы, дашборды. Используется в реальном времени.

Нельзя одно подменять другим.

**Обоснование.** Audit без observability = ты узнаёшь о пожаре по фотографии пепелища. Observability без audit = ты видишь, что что-то горит, но не можешь восстановить причину.

**Пример нарушения.** Логи в файл, никаких метрик. Через неделю выясняется, что пайплайн жёг $200 в день на retry-цикле, никто не заметил.

**Критерий слома.** Для маленького личного проекта observability может быть просто `tail -f` — но решение должно быть осознанным, не «забыли».

---

## B7. Cost и budget guardrails — отдельный класс хуков

**Правило.** На каждый LLM-вызов и на каждый пайплайн в целом — явный budget (токены, доллары, время, retry count). Превышение = hard-halt, не warning.

**Обоснование.** Агентные системы умеют незаметно жечь деньги в циклах. «Оркестратор запускает оркестраторов» без budget = неограниченная экспоненциальная история.

**Пример нарушения.** LLM-агент в цикле «не получилось — попробую ещё раз» без счётчика. К утру баланс на нуле.

**Критерий слома.** Когда budget становится слишком тесным и блокирует легитимную работу — пересматривай дизайн, не повышай лимит молча.

---

## B8. Human-in-the-loop как отдельный класс, не как hard-halt

**Правило.** Необратимые или дорогие операции (удаление данных, отправка внешних сообщений, платежи, изменение прода) требуют явного approval gate **до** действия, не halt **вместо** действия.

**Обоснование.** Hard-halt — это «что-то пошло не так, помоги». Approval gate — это «всё штатно, но решение требует человека». Смешивать их = либо человек не реагирует на halt-ы (потому что их слишком много, в основном штатные), либо штатные действия блокируются как ошибки.

**Пример нарушения.** Агент «по умолчанию отправляет письмо клиенту, halt если не уверен». Должно быть наоборот: «по умолчанию готовит черновик и ждёт approval, halt если черновик не удалось сформировать».

**Критерий слома.** Когда approval gates становятся узким местом и человек апрувит всё подряд не глядя — gate перестал работать, нужен либо более узкий критерий, либо автоматизация под аудит.

---

## B9. Rollback и compensating actions для операций с внешним миром

**Правило.** Любая операция, меняющая состояние вне твоей системы (внешний API, email, БД третьей стороны), должна идти через outbox-паттерн или иметь явное compensating action.

**Обоснование.** Audit trail покажет, что письмо было отправлено перед падением шага 6. Но это уже произошло. Если за этим письмом должен был последовать платёж, который не прошёл — у тебя рассогласованное состояние.

**Пример нарушения.** Шаг 5 → API-вызов → шаг 6 падает → перезапуск с шага 5 → второй API-вызов. Никто не знает, что в системе произошло.

**Критерий слома.** Когда compensating action невозможен (например, физическое действие в реальном мире) — нужен либо human-in-the-loop, либо двухфазное подтверждение, но «просто надеяться, что не упадёт» — не вариант.

# Уровень 3. Мета-правила

## C1. Три патча одного класса = СТОП-сессия

**Правило.** Если за последние 3 итерации одной области ты внёс 3 быстрых фикса без появления таксономии — следующая сессия начинается с enumeration, ноль кода.

**Обоснование.** Это главное правило против reactive-patch trap. Большинство деградаций систем идёт именно отсюда: вместо понимания причины класса проблем накапливаются точечные заплатки.

**Пример нарушения.** «Тут ещё один edge case, давай быстро добавим if». В третий раз. В пятый раз. Через месяц никто не понимает, что происходит в этой функции.

**Критерий слома.** Иногда 3 фикса действительно покрывают разные проблемы, не один класс. Тогда нужно явно зафиксировать: «это были три разных явления, вот почему», и продолжить.

---

## C2. «Давай быстро починим» = красная лампочка

**Правило.** Когда LLM или ты сам предлагаешь quick patch — обязательный вопрос: «это N-й патч того же класса?». Если N ≥ 2 → таксономия, не patch.

**Обоснование.** «Давай быстро» — это эвристика «не хочу думать сейчас». В большинстве случаев это правильно. В случаях с систематическими проблемами — это путь к разрушению дизайна.

**Пример нарушения.** «Просто добавим try/except здесь, потом разберёмся». «Потом» не наступает.

**Критерий слома.** Для одноразовых скриптов и прототипов quick patch — норма. Правило применяется к системам, у которых есть будущее.

---

## C3. Audit trail обязателен для каждого решения системы

**Правило.** Каждое решение, принятое системой (особенно LLM-воркером), — артефакт на диске. `events.jsonl`, `state.json`, `decision-log.md`. Никаких «LLM решил у себя в голове» без записи.

**Обоснование.** Без audit trail отладка агентной системы — это шаманизм. Ты не можешь спросить «почему вчера агент выбрал ветку B?» без записи входа, промпта, выхода и метаданных.

**Пример нарушения.** Логируется только финальный результат пайплайна. Промежуточные решения — нигде. На вопрос «почему» ответ «не знаю».

**Критерий слома.** Когда audit trail становится больше полезного выхода (например, миллион событий в день на терабайт логов) — нужна агрегация и retention policy, но не отказ от audit.

---

## C4. Не вся ценная работа измеряется строчками кода

**Правило.** Definition of Done для design-сессии — это документ, который позволит другому человеку (или тебе через месяц) принять то же решение без повторной дискуссии. Если в git log один markdown-файл — ты сделал работу выше уровнем чем код.

**Обоснование.** Сессии бывают двух типов: feature-добавляющие (растёт код) и design-замораживающие (растёт понимание). Путать их = либо писать код без понимания, либо обсуждать бесконечно без артефактов.

**Пример нарушения.** «Поговорили час, ничего не написали, сессия пропала зря». Если был enumeration + taxonomy + design doc — нет, не пропала.

**Критерий слома.** Если design-сессии становятся способом избегать имплементации — это уже не дисциплина, а прокрастинация. Должна быть пропорция: design ≤ implementation по времени в долгосроке.

---

## C5. После каждой сессии — явная классификация её типа

**Правило.** В конце сессии задай себе вопрос: «это была feature-сессия, design-сессия, debug-сессия, refactor-сессия?». Зафиксируй ответ. Если не можешь классифицировать — это сигнал, что сессия была расфокусированной.

**Обоснование.** Типы сессий требуют разной дисциплины. Feature-сессия без enumeration → reactive-patch. Design-сессия с кодом → преждевременная оптимизация. Debug без воспроизведения → шаманизм.

**Пример нарушения.** «Просто работал». Через неделю не понимаешь, что было сделано и зачем.

**Критерий слома.** Иногда сессия легитимно смешанная (нашёл баг во время фичи). Тогда в логе — две записи, не одна.

---

## C6. Каждая абстракция должна иметь явный критерий, когда она ломается

**Правило.** Для каждого правила, паттерна, абстракции — явно сформулируй: «это работает до тех пор, пока...». Без критерия слома правило превращается в догму.

**Обоснование.** Реальность сложнее любого правила. Правило без критерия слома применяется там, где оно вредит. Правило с критерием слома — это инструмент.

**Пример нарушения.** «У нас всегда X». Без объяснения, при каких условиях X перестаёт работать. Через год X применяется в ситуации, для которой не создавался, и ломает систему.

**Критерий слома.** У этого мета-правила тоже есть слом: если ты тратишь на формулировку критерия слома больше, чем на само правило — правило, возможно, слишком частное.

# Чек-лист перед стартом проекта

Прежде чем писать первую строку кода в новом агентном проекте:

- [ ] Я могу нарисовать пайплайн как state machine (узлы = состояния, рёбра = переходы)
- [ ] Для каждого узла я знаю: это форма (скрипт) или смысл (LLM)
- [ ] Для каждого артефакта есть схема и версия
- [ ] Для каждого шага есть retry-семантика (идемпотентен или есть compensating action)
- [ ] Есть budget (токены/деньги/время) на пайплайн и hard-halt при превышении
- [ ] Есть audit trail (events на диске) и хотя бы базовая observability (метрики)
- [ ] Для необратимых операций есть approval gate, не halt
- [ ] Для каждого LLM-выхода, попадающего в код/состояние/мир, есть детерминированный валидатор
- [ ] Я знаю критерий слома для каждого ключевого решения дизайна

# Чек-лист перед каждой сессией

- [ ] Над чем именно я работаю? (одно предложение)
- [ ] Сколько раз я уже патчил эту область? Если ≥ 3 — enumeration, ноль кода.
- [ ] Тип сессии: feature / design / debug / refactor?
- [ ] Definition of Done для этой сессии (что в git/диске после неё)?

# Чек-лист после каждой сессии

- [ ] Тип сессии подтверждён?
- [ ] Артефакт создан (код или документ)?
- [ ] Если были quick patch'и — пора ли в следующую сессию делать taxonomy?
- [ ] Что я узнал, чего не знал в начале?
