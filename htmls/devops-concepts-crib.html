1 · SDLC — жизненный цикл разработки

SDLC (Software Development Life Cycle) — слово-ЗОНТИК, не технология:
все этапы жизни софта от идеи до эксплуатации, по кругу.

     ┌────────────────────────────────────────────────────┐
     ▼                                                    │
   идея → анализ → дизайн → РАЗРАБОТКА → тесты → деплой → эксплуатация
                                                  │            │
                                                  ▼            ▼
                                            (наш конвейер   (мониторинг,
                                             CI/CD живёт    heartbeat,
                                             ЗДЕСЬ)         shift-right)
Ты это уже знаешь под другим именем: BMAD Phase 1-5 (Analysis → Planning → Solutioning → Implementation → …) — один из вариантов SDLC. «AI-native SDLC» = как этот цикл перестраивается, когда код пишет агент: медленный CI больше не блокирует человека → можно гонять больше проверок; зато нужен контроль САМОГО агента (ревью его кода, защита workflow-файлов от его правок).

2 · Две модели веток — где живёт код до main

GITHUB FLOW (мы прошли его руками, круги №1-2):
  ветка живёт ДНЯМИ, в main въезжает через PR со скрепкой

  main ────●─────────────────M──────────────M────►
            \               /              /
             ●───●───●─────┘      ●───●───┘
             dev: 3 коммита       dev: 1 коммит
             (PR #2)              (PR #3)

TRUNK-BASED (стандарт элитных команд по DORA):
  trunk = «ствол» = main. Коммитят ПРЯМО в него (или ветка живёт < 1 дня).
  Каждый коммит мал — часы работы, не дни.

  main ──●──●──●──●──●──●──●──●──●──●──►
         ▲ качество держит ЖЕЛЕЗНЫЙ CI на каждый push
         ▲ недоделанное едет ВЫКЛЮЧЕННЫМ (feature-флаг)
GitHub FlowTrunk-based
веткиживут дняминет, или < 1 дня
ревьюв PR, ПЕРЕД mergeпарно до коммита, или после факта
что держит качествоворота на PR (CI + protection)очень сильный CI на каждый push + флаги
недоделанная фичасидит в веткевъезжает в main ВЫКЛЮЧЕННОЙ (feature-флаг)
больдолгая ветка уезжает от main → тяжёлый mergeбез железного CI main быстро краснеет
кому хорошкоманды с обязательным ревью; новичкизрелые команды с полным CI (DORA elite)
⚔️ Почему длинные ветки — зло: чем дольше ветка живёт, тем дальше уезжает от main и тем больнее merge. Наш собственный шрам: интеграционная ветка на 10+ коммитов → rename+modify конфликты (см. скилл git-merge-integration). Оба лагеря согласны в главном: вливаться надо часто и мелко — спор только о том, нужна ли остановка-PR по дороге.

3 · Feature-флаг — ключ к trunk-based

недоделанный код УЖЕ в main и УЖЕ на проде — но ВЫКЛЮЧЕН:

  if flags.new_search:        # флаг off → старый путь работает
      new_search()            # код едет в прод «спящим»
  else:
      old_search()

включение = переключить флаг (без деплоя!) · сломалось = выключить (kill-switch)
Ты это уже практикуешь сам: «off by default, canary-armed» в overlay_sync (текст-канарейка за флагом --text-canary / env) — ровно этот приём. Деплой кода и ВКЛЮЧЕНИЕ поведения — два отдельных события.

4 · Соло + LLM-агент: какую модель брать?

обычный соло:  «ревьюить некому → PR = театр одного актёра?»
               trunk-based говорит: коммить в main, CI на push удержит

НО у тебя есть то, чего нет у обычного соло:
               код пишет АГЕНТ ──► PR = единственное место, где ты
               видишь его работу ЦЕЛИКОМ до попадания в main
               + точка для LLM-ревью и required checks
✅ РЕШЕНО ресерчем (DORA 2025 + trunkbaseddevelopment.com + практика 2026): берём GitHub Flow с КОРОТКИМИ ветками — одна спека = одна ветка = один маленький PR = merge в тот же день. Trunk-based официально разрешает соло коммитить прямо в main, но это рассчитано на «автор кода = человек, который его понимает». С агентом PR — единственное место, где человек читает дифф до попадания в main, и единственная точка, куда вешаются required checks ДО merge (в trunk-based ворота стоят после).

4б · Две оси — не путать (частая ошибка)

ОСЬ 1 — МОДЕЛЬ ВЕТОК     «где живёт код, пока не попал в main»
        Git Flow · GitHub Flow · Trunk-based
        ↑ это ТОЛЬКО про ветки. Ни слова про тесты.

ОСЬ 2 — ВОРОТА           «что проверяет код по дороге»
        pre-commit · CI · required checks · ревью · rulesets
        ↑ навешиваются на ЛЮБУЮ модель веток, независимо

Все три модели различаются ТОЛЬКО длиной жизни ветки:
   Git Flow      недели-месяцы  ──► merge hell        ❌ против DevOps
   GitHub Flow   часы-дни       ──► мелко и часто     ✅ наш
   Trunk-based   минуты-часы    ──► ещё мельче        ✅ радикальнее
⚠️ Git Flow ≠ GitHub Flow — одна буква, противоположные вещи. Устарел ПЕРВЫЙ (5 типов веток, релизы редко). «Накопление коммитов», которого боятся, — свойство не GitHub Flow, а ДЛИННОЙ ветки. Держи ветку короткой — накопления нет по построению.

4в · Что НЕ изменится, чем бы ты ни занимался

РУЧКА 1: кто пишет код (человек / АГЕНТ)      ← главная, двигает ЯДРО решений
РУЧКА 2: масштаб и клиенты (скрипт / продукт) ← двигает только ХВОСТ
Вывод (ядро)Почему привязан к агенту, а не к размеру продукта
PR обязателенединственная точка, где человек читает дифф агента
мелкие батчи ДО генерациирезать задачу, а не готовый результат: AI-PR раздуты на 51-154%, ревью такого диффа не происходит

--no-verify под запретомпрецедент обхода в истории = обучающий пример: агент читает историю и повторяет
прод отдельно от папки агентаиначе незакоммиченная правка агента мгновенно становится продом
деплой: fetch + reset --hard, не pullpull делает merge — мусор на проде тихо ломает автодеплой; прод = ТОЧНАЯ копия main

4г · Что дорастёт вместе с продуктом

Сейчас (скрипт, клиентов нет)Станет (продукт с клиентами)
staging — skip (дорог и врёт; заменяет --dry-run на реальных данных + быстрый откат)нужен эквивалент: ephemeral-среды на PR или canary-выкатка
release-процесс — skip: «deploy main» + git tag перед рискованным (закладка для отката)версии semver, теги релизов, changelog для внешних потребителей
порог покрытия — skipпоявится как required status check
merge queue — недоступна и не нужнапри потоке PR от нескольких авторов
smoke = --version + конфиг + dry-runhealth-эндпоинты, синтетический мониторинг из разных регионов
ревью = LLM-отчёт + твоё решение+ человек-ревьюер, CODEOWNERS, обязательные аппрувы
🔑 Как читать любую новую практику: не «индустрия делает — значит надо», а какую проблему это решает и есть ли она у меня. Все три «skip» выше — решения проблем, которых у тебя нет: staging решает «страшно катить на живых клиентов» (клиентов нет), релиз-процесс — «внешние потребители версий» (потребителей нет), Git Flow — «параллельная поддержка версий» (версия одна).

4д · Одна решётка на четырёх системах

Конструкция ОДНА, реализаций ЧЕТЫРЕ. Понял одну — читаешь все:

    СОБЫТИЕ  ──►  ФИЛЬТР  ──►  ИСПОЛНИТЕЛЬ  ──►  УЗЕЛ ИСХОДОВ
   (сито 1)     (сито 2/3)      (кто судит)     (что он может)

  Claude-харнесс   settings.json           ← правит поведение АГЕНТА
  локальный git    .pre-commit-config.yaml ← ловит МОЙ коммит        (ступень 1)
  GitHub Actions   .github/workflows/      ← ловит то, что уехало    (ступень 3)
  ─────────────────────────────────────────────────────────────────────────
  RULESET          настройка на серверах GitHub, В РЕПО ЕЁ НЕТ       (ступень 2)
⚠️ Различие, ради которого таблица и нужна — не в ситах, а в УЗЛЕ ИСХОДОВ. У харнесса и у git вердикт хука = приговор (exit 2 останавливает). У Actions красный чек — только надпись, кнопка Merge остаётся живой. Приговором её делает ruleset — отдельный слой, который не является хуком вообще. Отсюда и порядок лестницы: ступень 3 без ступени 2 краснеет в пустоту.
🔑 Ruleset выпадает из ряда дважды: ① его рецепт единственный не лежит в репозитории — не виден в диффе, не версионируется, агент его не прочитает; ② он единственный ничего не запускает — читает не наш конфиг, а имя job и его цвет. Слеп к содержанию: переименовал job — проверка «исчезла»; job из одной строки echo ok — пропустит с чистой совестью.

Полная решётка по колонкам (событие · матчер · if · сито в скрипте · исполнитель · чем обходится) — в claude-code-hooks-map, раздел «Четыре системы рядом». Цепочки «как каждая доходит до конфига» — там же и в git-pipeline-master. Здесь только концепция, чтобы один факт не жил в трёх файлах.

4е · Чего хуком не построить

ХУК = РЕАКЦИЯ НА СОБЫТИЕ
   └─► значит физически не срабатывает, когда события НЕ БЫЛО
цельмеханизмэто хук?
поймать грязный код до коммитаpre-commit✅ да
прогнать проверки на сервереActions⚠️ похож, но это workflow
запретить merge при красномruleset❌ свойство ветки
суждение о смысле правкиревью (человек / LLM)❌ суждение
«тестов не написали вовсе»покрытие как required check❌ измерение по факту прогона
«прогон вообще не случился»dead man's switch / heartbeat❌ тревога на ТИШИНУ
🔍 Две последние строки различать обязательно. Покрытие говорит «код есть, тестов на него нет» — но только когда прогон состоялся. Если прогона не было вовсе, отчёта нет, и молчание неотличимо от «всё хорошо». Ловит это лишь внешний наблюдатель: упавший сторож о своём падении не сообщает. Тот же закон, по которому канарейка не проверяет сама себя.
📦 Ещё одна поправка: push — не резервная копия. Off-site копия появляется как побочный эффект, но git push --force или удаление репозитория уничтожают обе стороны одной операцией. Бэкап требует независимости от того, кто им управляет. Цель GitHub Flow другая — место, где человек читает дифф до попадания в main.

5 · Словарь рядом

терминсуть одной строкой
SDLCзонтик: все этапы жизни софта, от идеи до эксплуатации
trunk«ствол» — главная ветка (main)
DORAисследование DevOps-эффективности (Google): метрики частоты/скорости/надёжности релизов; «elite» команды = trunk-based
feature-флагвыключатель куска функциональности в рантайме, без деплоя
kill-switchтот же флаг в роли «мгновенно вырубить сломанное»
merge hellболь слияния долгой ветки, уехавшей от main
CI / CDcontinuous integration (проверки до merge) / continuous delivery-deployment (доставка после)
shift-left / shift-rightдвигать проверки раньше (дешевле поймать) / проверять уже в проде (часть багов видна только там)
rulesetправило ветки на стороне GitHub: единственный слой, который реально запрещает merge/push; его рецепт не лежит в репозитории
required checkимя job'а, объявленное обязательным в ruleset: не зелёный или не пришёл — merge заблокирован
покрытие (coverage)доля кода, затронутая тестами при прогоне; ловит «тестов не написали», но молчит, если прогона не было
dead man's switchвнешний наблюдатель, который бьёт тревогу на отсутствие сигнала; единственное, что ловит «проверки не запускались вовсе»
склад хуков~/.cache/pre-commit — скачанные инструменты; вне git, восстановим из рецепта по хешу, потому и не коммитится
