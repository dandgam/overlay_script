0а · Четыре слова: репозиторий · ветка · worktree · remote

терминчто это ФИЗИЧЕСКИсколько у нас
Репозиторий (разг. «репо»)проект + ВСЯ история — папка .git2: локальный + копия на GitHub
Веткаименованный УКАЗАТЕЛЬ на коммит (строка внутри .git)много: dev, main, …
WorktreeРАБОЧАЯ ПАПКА: файлы на диске, разложенные по одной ветке4 у локального репо
Remoteсохранённый АДРЕС чужого репозитория + короткое имя1: script → GitHub
РЕПОЗИТОРИЙ №1 (твоя машина) — история ОДНА на все папки
├── ВЕТКИ (указатели в .git):  dev → 5138136 · main → 4a6342d · …
└── WORKTREE (папки на диске, каждая на СВОЕЙ ветке):
    ├── ~/bmad-orchestrator             ← dev   (тут кодишь)
    ├── /home/server/overlay_sync_prod  ← main  (ПРОД)
    └── .claude/worktrees/agent-…×2     ← ветки агентов-воркеров

        ▲ push / pull ▼   через remote «script»

РЕПОЗИТОРИЙ №2 (GitHub, dandgam/overlay_script) — ОТДЕЛЬНАЯ копия истории
└── ветки: script/dev · script/main
🔑 Ветка = запись в истории, worktree = файлы на диске. Обычно папка одна и ты переключаешь её (git switch) — файлы перезаписываются. Worktree даёт НЕСКОЛЬКО папок сразу, каждую на своей ветке. Следствия: ① одна ветка = максимум одна папка (main занята продом → git switch main здесь откажет, знак + в branch -vv); ② история ОБЩАЯ — коммит из любой папки виден всем, потому прод обновляется обычным git pull, а не копированием файлов.

0 · Карта трёх позиций — держать в голове всегда

①  dev            моя ЛОКАЛЬНАЯ ветка (указатель на коммит)
②  script/dev     мой КЭШ знаний о GitHub (протухает! обновляет fetch/push)
③  GitHub         живой сервер

ls-remote  смотрит ③, ничего не двигает          (градусник, read-only)
fetch      двигает ② → ③                          (кэш освежить, работу не трогает)
pull       = fetch + merge: двигает ② И ①         (может принести конфликт)
push       двигает ③ ← ① (и ② заодно)             (действие НАРУЖУ — видно другим)

1б · Индекс — что именно попадёт в коммит

командачто даёт
git status --shortкомпактный список: буква слева = состояние в индексе (легенда ниже)
git diff --cached --name-onlyровно список файлов будущего коммита — без содержимого
git diff --cachedто же, но с содержимым: что именно уедет в коммит
буквазначение
Aдобавлен в индекс (новый файл, прошёл git add)
Mизменён (слева = изменение в индексе, справа = ещё не добавлено)
Dудалён
Rпереименован
??git о файле не знает вовсе (untracked)
🧱 Когда пригодилось (ступень 1 ворот, 2026-08-04): хук завернул коммит — возник вопрос «а что теперь с файлами?». Ответ: коммит атомарен — либо весь, либо ничего, это свойство git, а не хука. Ничего не теряется: индекс цел, правки на диске целы, не создан только коммит. Эти три команды показывают, что осталось в индексе.
Убрать один файл из коммита, не удаляя с диска: git restore --staged путь/файл.
📌 --cached = «смотри в ИНДЕКС, а не в рабочую папку». Без него git diff показывает противоположное — что изменено, но ещё не добавлено.

командачто даёт

Повседневная пара: git fetch script → git branch -vv. Остальное — спецмерки при странностях.

2б · Кто я / привязка / три хэша — точечные команды

вопроскомандаувидишь
на какой я ветке?git branch --show-currentdev
с кем она связана?git rev-parse --abbrev-ref @{u}script/dev (@{u} = @{upstream}, привязка ТЕКУЩЕЙ ветки; ошибка = ветка-сирота)

хэш ② кэшаgit rev-parse @{u}(или git rev-parse script/dev)

чтение трёх хэшей:
  ①=②=③   полная синхронизация
  ①≠②=③   накоммитил локально, push ещё не делал (ahead)
  ①=②≠③   КЭШ ПРОТУХ — на сервере новое → git fetch script

2в · Ветки: создать · переключиться · привязать · удалить

командачто даёт
git switch имяпереключиться на существующую ветку
git switch -c имясоздать новую от текущего коммита и перейти на неё
git switch -c имя точкасоздать от указанной точки (хэш / main / script/main)
git push -u script имяПЕРВЫЙ push новой ветки: создаёт её на GitHub + записывает привязку (-u = --set-upstream, один раз; дальше хватает голого git push)
git branch -m старое новоепереименовать локальную ветку
git branch -d имяудалить локальную (откажет, если не влита — защита; форс -D осознанно)
git push script --delete имяудалить ветку НА GitHub (действие наружу!)
git worktree listвсе рабочие копии репо. Знак + у ветки в branch -vv = она ЗАНЯТА другим worktree, переключиться сюда нельзя (наш прод: /home/server/overlay_sync_prod на main)
Ветка на GitHub рождается в момент первого push -u — заранее заводить не надо. Имя локальной и серверной может различаться (git push script лок:серв), но одинаковые имена = конвенция, спасающая рассудок.

3б · Забрать чужое: git pull

git pull  =  git fetch  +  git merge     ← ЕДИНСТВЕННАЯ команда, что двигает ① и ФАЙЛЫ на диске
                                            (потому только она умеет дать КОНФЛИКТ)

три исхода — смотри git rev-list --left-right --count dev...script/main ДО:
  0 N   своего нет      → fast-forward: указатель просто перемотан, новых коммитов НЕТ
  M N   оба ушли вперёд → создаст MERGE-КОММИТ (скрепку с двумя родителями)
  правки в тех же строках → КОНФЛИКТ, разрешаешь руками
командачто даёт
git pullиз привязки @{u}: стоя на dev → возьмёт script/dev
git pull script mainявно: взять script/main → влить в ТЕКУЩУЮ ветку (источник указан, приёмник всегда там, где стоишь — легко влить не туда!)
git pull --ff-onlyхорошая привычка: только перемотка; нужен merge-коммит → откажется, решаешь сам
git pull --rebaseвместо скрепки перенести СВОИ коммиты поверх чужих (история линейная). Опасно после push — переписывает хэши

5 · Правила безопасности (куплены уроками)

🚫 amend / rebase ТОЛЬКО до push. После push история append-only: правки — новым коммитом. (Хэш при amend меняется → у сервера была бы другая история.)
🚫 Никогда --force, --no-verify, reset --hard без явного решения с холодной головой.
👀 add -A → всегда git status перед commit: смотри, ЧТО кладёшь.
📡 git status сравнивает с КЭШЕМ ②: «up to date» ≠ правда сервера. Сомнение → fetch сначала.
✍️ Сообщение пишется 1 раз — читается десятки. «html» = слепая строка в оглавлении истории.

6 · Канонический круг: код → PR → main → прод

① кодим + коммитим                              локально, ветка dev
② git push                                      dev ──────► script/dev
③ PR + merge на GitHub (Create a merge commit)  script/dev ──► script/main
      ▲ ЗДЕСЬ рождается СКРЕПКА — новый коммит с ДВУМЯ родителями.
        Потому хэш main ≠ хэш dev. (Squash/rebase не берём: squash слепит
        коммиты в один, rebase перепишет хэши.)
④ git pull --ff-only script main                script/main ──► dev  (перемотка:
      ▲ твой коммит — РОДИТЕЛЬ скрепки, значит предок → указатель просто едет вперёд)
⑤ git push                                      dev ──────► script/dev  (закрыть ahead 1)
⑥ git -C /home/server/overlay_sync_prod pull --ff-only script main   ──► ПРОД
шагкто двигаетсягде происходит
②script/devмашина → GitHub
③script/main + скрепкана GitHub
④локальная devмашина ← GitHub
⑤script/devмашина → GitHub
⑥прод-worktreeмашина ← GitHub
🏠 Репозиторий ОДИН — две рабочие папки на разных ветках (worktree): ~/bmad-orchestrator = dev · /home/server/overlay_sync_prod = main (прод). История общая. Отсюда + в branch -vv и -C путь вместо cd.
⬇️ Деплой у нас pull-based: прод сам ЗАБИРАЕТ проверенный main (входящих подключений к машине нет — облачный runner до неё не дотянется). Гарантия качества приходит не из деплоя, а из ворот ДО main.
