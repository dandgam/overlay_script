терминчто это ФИЗИЧЕСКИсколько у нас
Репозиторий (разг. «репо»)проект + ВСЯ история — папка .git2: локальный + копия на GitHub
Веткаименованный УКАЗАТЕЛЬ на коммит (строка внутри .git)много: dev, main, …
WorktreeРАБОЧАЯ ПАПКА: файлы на диске, разложенные по одной ветке4 у локального репо
Remoteсохранённый АДРЕС чужого репозитория + короткое имя1: script → GitHub
РЕПОЗИТОРИЙ №1 (твоя машина) — история ОДНА на все папки
├── ВЕТКИ (указатели в .git):  dev → 5138136 · main → 4a6342d · …
└── WORKTREE (папки на диске, каждая на СВОЕЙ ветке):
    ├── ~/bmad-orchestrator             ← dev   (тут кодишь)
    ├── /home/server/overlay_sync_prod  ← main  (ПРОД)
    └── .claude/worktrees/agent-…×2     ← ветки агентов-воркеров

        ▲ push / pull ▼   через remote «script»

РЕПОЗИТОРИЙ №2 (GitHub, dandgam/overlay_script) — ОТДЕЛЬНАЯ копия истории
└── ветки: script/dev · script/main
🔑 Ветка = запись в истории, worktree = файлы на диске. Обычно папка одна и ты переключаешь её (git switch) — файлы перезаписываются. Worktree даёт НЕСКОЛЬКО папок сразу, каждую на своей ветке. Следствия: ① одна ветка = максимум одна папка (main занята продом → git switch main здесь откажет, знак + в branch -vv); ② история ОБЩАЯ — коммит из любой папки виден всем, потому прод обновляется обычным git pull, а не копированием файлов.

0 · Карта трёх позиций — держать в голове всегда

①  dev            моя ЛОКАЛЬНАЯ ветка (указатель на коммит)
②  script/dev     мой КЭШ знаний о GitHub (протухает! обновляет fetch/push)
③  GitHub         живой сервер

ls-remote  смотрит ③, ничего не двигает          (градусник, read-only)
fetch      двигает ② → ③                          (кэш освежить, работу не трогает)
pull       = fetch + merge: двигает ② И ①         (может принести конфликт)
push       двигает ③ ← ① (и ② заодно)             (действие НАРУЖУ — видно другим)

1б · Индекс — три состояния одного файла

У КАЖДОГО файла ТРИ состояния ОДНОВРЕМЕННО. Это не метафора — их можно прочитать по отдельности:

  РАБОЧАЯ ПАПКА   то, что ты видишь и правишь           обычный файл на диске
  ИНДЕКС          снимок, подготовленный к коммиту      внутри .git/, НЕ файл
  HEAD            последний коммит                      внутри .git/

git add = СФОТОГРАФИРОВАТЬ файл прямо сейчас и положить фото в индекс.
          Дальше файл живёт своей жизнью — фотография НЕ обновляется.
командачто даёт
git status --shortкомпактный список; ДВЕ буквы слева — легенда ниже
git diffдиск ↔ индекс: «что я наменял, но не добавил»
git diff --cachedиндекс ↔ HEAD: «что уедет в коммит» (с содержимым)
git diff --cached --name-onlyто же, только список файлов
cat путь/файлсодержимое с диска — то, что видишь
git show :путь/файлсодержимое из индекса — то, что закоммитится. Двоеточие в начале пути = «достань из индекса»
git show HEAD:путь/файлсодержимое из последнего коммита
git restore --staged путь/файлубрать файл из индекса, не удаляя с диска

XY  файл

└── первая колонка: ИНДЕКС (добавлено)

D удалён✅

1г · ЛОВУШКА «я же починил, а в коммите старое»

① пишешь функцию с багом              диск: A(баг)   индекс: —
② git add file.py                     диск: A        индекс: A(баг)
③ запускаешь, видишь баг, ЧИНИШЬ      диск: B(ок)    индекс: A(баг)   ← РАЗОШЛИСЬ
④ git commit -m "фикс бага"           в историю ушла A. БАГ В РЕПОЗИТОРИИ
⑤ git push                            баг уехал на GitHub
⑥ прод: fetch + reset --hard          баг в проде
⑦ у тебя локально лежит B, всё работает, ты уверен что починил
🎭 Шаг ⑦ — самый коварный. Классическое «у меня работает» рождается ровно здесь. Ты не врёшь: ты смотришь на диск, а прод смотрит на историю. Пока не сравнишь cat файл с git show :файл — расхождения не увидишь.
🧪 Воспроизвести за минуту (опыт 2026-08-05, безопасно, без коммита):
printf 'версия A\n' >probe.txt → git add probe.txt → printf 'версия B\n' >probe.txt
затем git status --short покажет AM, а cat probe.txt и git show :probe.txt дадут разное содержимое в одну и ту же секунду.
Уборка: git restore --staged probe.txt → rm probe.txt.
🛡️ Три способа не попасть: ① git add -A перед коммитом — добавить всё · ② git commit -a — сам добавит изменённые отслеживаемые (но НЕ новые файлы!) · ③ привычка смотреть git status перед коммитом, а не после.
⚙️ Ступень 1 ворот эту ловушку закрывает. Фреймворк pre-commit перед прогоном прячет всё недобавленное ([INFO] Stashing unstaged files… в свой склад, не через git stash) и возвращает после. Хуки видят РОВНО будущее состояние репозитория. Без этого хук прочитал бы с диска починенную B, а в историю ушла бы A с багом — ворота отчитались бы зелёным о том, чего не проверяли.
В CI стэш не нужен: раннер делает checkout, рабочая папка равна коммиту по определению, индекса с «недобавленным» там не существует.
🧱 Коммит атомарен — либо весь, либо ничего. Свойство git, а не хука: хук вернул не-ноль → коммит не создан целиком. Ничего не теряется — индекс цел, правки на диске целы. Частичных коммитов не бывает: иначе в истории оказалось бы состояние, которого никто не проверял.
📌 --cached = «смотри в ИНДЕКС, а не в рабочую папку». Без него git diff показывает ровно противоположное — что изменено, но ещё не добавлено.

1д · Откатить: git restore — вопрос только «откуда и куда»

git restore [--source=ОТКУДА] [--staged] [--worktree] файл
                    │              │            │
              из какого        писать в     писать на
              коммита          ИНДЕКС       ДИСК

⚠️ БЕЗ флагов restore пишет НА ДИСК — это самый опасный вариант.
командаберёт изпишет вопасность
git restore --staged файлHEADиндекс✅ безопасно — диск не тронут (файл снова становится «??»)
git restore файлиндексдиск🔴 затирает твои правки НАВСЕГДА
git restore -SW файлHEADиндекс + диск🔴🔴 сносит всё несохранённое (-S = --staged, -W = --worktree)
git restore --source=HEAD~3 файлкоммит HEAD~3диск⚠️ перезапишет диск версией трёхкоммитной давности
💀 Почему git restore файл необратим. Правки, лежащие только на диске, git не хранил ни секунды: в индексе их нет, в истории нет, нигде нет. Перезапись диска стирает их без следа — отменить нечем, git не может вернуть то, о чём никогда не знал. Единственная страховка — коммитить часто.
🕰️ Историческая справка — пригодится при чтении старых гайдов. Раньше обе задачи решал перегруженный git checkout, и это была известная ловушка: одна команда с тремя разными смыслами.
git checkout -- файл → git restore файл (вернуть файл с диска)
git reset HEAD файл → git restore --staged файл (убрать из индекса)
git checkout ветка → git switch ветка (переключить ветку — вынесли отдельно)
Старые формы всё ещё работают, но новые разделены по смыслу, и ошибиться труднее.
🧭 Правило перед любым restore: сначала git status --short. Если у файла во второй колонке есть буква — на диске лежит то, чего нет больше нигде. Сохрани это (коммитом или копией) прежде чем откатывать.

2г · Предпросмотр PR — что именно уедет в main / прод

Две точки читаются как «РАЗНИЦА»: что есть СПРАВА, но нет СЛЕВА.

  main..dev   →  что есть в dev, но ещё НЕ доехало до main (= до прода)
  dev..main   →  наоборот: что есть в main, но нет у меня
командачто даёт
git log --oneline main..devкакие коммиты уедут — список хэшей и сообщений
git diff main..dev --statкакие файлы изменятся + сводка «сколько строк ±»
git diff main..devполный дифф: что именно уедет, построчно
git fetch script → git diff script/main..dev --statто же, но против реального состояния GitHub, а не локальной копии main
👁️ Это ровно предпросмотр будущего PR. Тот же список файлов GitHub покажет на вкладке Files changed. Смотреть до открытия PR — дешевле, чем обнаружить лишний файл после ревью.
Второй вариант (через script/main) точнее: локальная main могла отстать, если давно не делал fetch.
🔀 Не путать два вопроса — это разные оси сравнения:
git diff HEAD · git diff --cached — «что у меня не закоммичено» (диск ↔ индекс ↔ HEAD, см. 1б)
git diff main..dev — «что закоммичено, но не доехало до main» (ветка ↔ ветка)

3б · Забрать чужое: git pull

git pull  =  git fetch  +  git merge     ← ЕДИНСТВЕННАЯ команда, что двигает ① и ФАЙЛЫ на диске
                                            (потому только она умеет дать КОНФЛИКТ)

три исхода — смотри git rev-list --left-right --count dev...script/main ДО:
  0 N   своего нет      → fast-forward: указатель просто перемотан, новых коммитов НЕТ
  M N   оба ушли вперёд → создаст MERGE-КОММИТ (скрепку с двумя родителями)
  правки в тех же строках → КОНФЛИКТ, разрешаешь руками
командачто даёт
git pullиз привязки @{u}: стоя на dev → возьмёт script/dev
git pull script mainявно: взять script/main → влить в ТЕКУЩУЮ ветку (источник указан, приёмник всегда там, где стоишь — легко влить не туда!)
git pull --ff-onlyхорошая привычка: только перемотка; нужен merge-коммит → откажется, решаешь сам
git pull --rebaseвместо скрепки перенести СВОИ коммиты поверх чужих (история линейная). Опасно после push — переписывает хэши

5 · Правила безопасности (куплены уроками)

🚫 amend / rebase ТОЛЬКО до push. После push история append-only: правки — новым коммитом. (Хэш при amend меняется → у сервера была бы другая история.)
🚫 Никогда --force, --no-verify, reset --hard без явного решения с холодной головой.
👀 add -A → всегда git status перед commit: смотри, ЧТО кладёшь.
📡 git status сравнивает с КЭШЕМ ②: «up to date» ≠ правда сервера. Сомнение → fetch сначала.
✍️ Сообщение пишется 1 раз — читается десятки. «html» = слепая строка в оглавлении истории.

6 · Канонический круг: код → PR → main → прод

① кодим + коммитим                              локально, ветка dev
② git push                                      dev ──────► script/dev
③ PR + merge на GitHub (Create a merge commit)  script/dev ──► script/main
      ▲ ЗДЕСЬ рождается СКРЕПКА — новый коммит с ДВУМЯ родителями.
        Потому хэш main ≠ хэш dev. (Squash/rebase не берём: squash слепит
        коммиты в один, rebase перепишет хэши.)
④ git pull --ff-only script main                script/main ──► dev  (перемотка:
      ▲ твой коммит — РОДИТЕЛЬ скрепки, значит предок → указатель просто едет вперёд)
⑤ git push                                      dev ──────► script/dev  (закрыть ahead 1)
⑥ git -C /home/server/overlay_sync_prod pull --ff-only script main   ──► ПРОД
шагкто двигаетсягде происходит
②script/devмашина → GitHub
③script/main + скрепкана GitHub
④локальная devмашина ← GitHub
⑤script/devмашина → GitHub
⑥прод-worktreeмашина ← GitHub
🏠 Репозиторий ОДИН — две рабочие папки на разных ветках (worktree): ~/bmad-orchestrator = dev · /home/server/overlay_sync_prod = main (прод). История общая. Отсюда + в branch -vv и -C путь вместо cd.
