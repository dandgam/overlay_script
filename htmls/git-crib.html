0 · Карта трёх позиций — держать в голове всегда

①  dev            моя ЛОКАЛЬНАЯ ветка (указатель на коммит)
②  script/dev     мой КЭШ знаний о GitHub (протухает! обновляет fetch/push)
③  GitHub         живой сервер

ls-remote  смотрит ③, ничего не двигает          (градусник, read-only)
fetch      двигает ② → ③                          (кэш освежить, работу не трогает)
pull       = fetch + merge: двигает ② И ①         (может принести конфликт)
push       двигает ③ ← ① (и ② заодно)             (действие НАРУЖУ — видно другим)

1 · Осмотреться

командачто даёт
git statusветка · чистота · что в staging · ahead/behind (vs кэш ②!)
git log --oneline -5последние 5 коммитов: хэш + сообщение (одна строка = один коммит)
git log --oneline --graph -10+ ASCII-схема веток и слияний
git log --oneline -- путь/файлкто и когда менял ЭТОТ файл
git show --stat HEADпоследний коммит: шапка + список файлов (HEAD~1 = предпоследний)
git show <хэш>коммит целиком с диффом (+ добавлено / − убрано)
git show <хэш>:путь/файлфайл ЦЕЛИКОМ, каким был в том коммите (машина времени)
git branch -vvлокальные ветки: где я (*), привязка [script/dev], ahead/behind
git remote -vподключённые удалённые репо (у нас один: script)
git worktree listвсе рабочие копии репо (в т.ч. прод /home/server/overlay_sync_prod)

2 · Сравнить ветки / позиции

командачто даёт
git fetch scriptосвежить кэш ② до правды сервера — ПЕРЕД любым сравнением
git rev-parse dev script/devхэши обеих точек (ветка = указатель; совпали = идентичны)
git ls-remote --heads script devхэш ветки НА СЕРВЕРЕ прямо сейчас (мимо кэша, read-only)
git rev-list --left-right --count dev...script/devсчёт расхождения: 1 0=я впереди · 0 0=идентичны · 2 1=разошлись
git log --oneline dev..script/devКАКИЕ коммиты есть у них, но нет у меня (две точки = разница)
Повседневная пара: git fetch script → git branch -vv. Остальное — спецмерки при странностях.

3 · Изменить и закоммитить

РАБОЧАЯ ПАПКА ──git add──► STAGING ──git commit──► ИСТОРИЯ ──git push──► GITHUB
 (файлы)                  (предбанник:            (навсегда,            (видно
                           состав будущего         append-only           другим)
                           коммита)                после push)
командачто даёт
git add путь/файлположить файл в staging (точечно — предпочтительно)
git add -Aсгрести ВСЁ изменённое+новое → обязателен взгляд в git status до коммита
git commit -m 'тип(скоуп): описание'коммит из staging; сообщение = enum-формат, по-русски
git commit --amend -m '…'переписать ПОСЛЕДНИЙ коммит (сообщение/состав). Хэш сменится!
git pushотправить коммиты на GitHub (привязка уже настроена → без аргументов)
git stash / git stash popзаначка: спрятать незаконченное вбок / вернуть (не путать со staging)

4 · Формат сообщения коммита (enum-словарь)

тип(скоуп): что сделано            ← по-русски, грепается: git log --oneline | grep 'fix('
типы:   feat · fix · docs · refactor · test · chore · infra
скоупы: dag · worker · merge-gate · policy · cli · sdk · spec · overlay-sync

5 · Правила безопасности (куплены уроками)

🚫 amend / rebase ТОЛЬКО до push. После push история append-only: правки — новым коммитом. (Хэш при amend меняется → у сервера была бы другая история.)
🚫 Никогда --force, --no-verify, reset --hard без явного решения с холодной головой.
👀 add -A → всегда git status перед commit: смотри, ЧТО кладёшь.
📡 git status сравнивает с КЭШЕМ ②: «up to date» ≠ правда сервера. Сомнение → fetch сначала.
✍️ Сообщение пишется 1 раз — читается десятки. «html» = слепая строка в оглавлении истории.
