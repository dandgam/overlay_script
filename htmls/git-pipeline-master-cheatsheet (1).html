Вот почему «GitHub-события на моём проде» не бывает: событие on:push фиксируется на серверах GitHub (куда прилетел push), а не на твоём ПК и не на проде. 💻 ПК и ☁️ GitHub — единственные места, где рождаются события. 🚀 Прод событий не имеет — он лишь получатель в конце, который сам забирает проверенный код (git pull) или принимает деплой. Даже если прод и дев на одной коробке — события всё равно «случаются» на GitHub, а машина общается с ними через push (туда) и pull (обратно).
И главное про проверки: они не встроены в точки. Точка = розетка (момент), проверка = прибор, который ставишь ты. Колонка «обязательность» ниже — это не «git так требует», а индустриальное «что стоит сделать гейтом, а что можно пропустить». В колонке верификаторов: (готовый: …) — берёшь готовый инструмент, (свой) — пишешь сам.
Инструменты в карте показаны на Rust. Для Python-проекта (наш bmad-orchestrator) подставляй эквиваленты — роли и места ТЕ ЖЕ, меняется только прибор: rustfmt → ruff format · clippy → ruff check · компилятор (типы) → mypy · cargo test → pytest · cargo-llvm-cov → pytest-cov · cargo-audit → pip-audit · cargo-deny (лицензии) → pip-licenses · cargo-mutants → mutmut · cargo-fuzz / property → hypothesis.

③ локальный merge если мерджишь на машине
pre-merge-commit
перед merge-коммитом
git-хук. Срабатывает ТОЛЬКО когда git merge создаёт merge-коммит. При fast-forward (частый случай: main не ушёл вперёд, git просто передвигает указатель — коммита нет) хук молча НЕ запускается; заставить: git merge --no-ff. При конфликте коммит-резолв проверяет pre-commit, не этот хук. Падает (exit≠0) → merge отменяется.
💻 ПК🟡 опц.если мерджишь локальноюнит на смерженном результате — тесты на коде ПОСЛЕ слияния (тесты пишешь сам, гоняет cargo test)ловит «по отдельности зелёные, вместе ломаются»▰▰▱▱ сек–миндве ветки могут быть зелёными по отдельности, но вместе сломаться по логике (не текст-конфликт, а поведение). Ловит это до запечатывания merge. Реже pre-commit — только при локальном merge (через PR на GitHub эту роль играет CI).

④ push
pre-push
перед отправкой
git-хук. Срабатывает при git push, перед отправкой на удалёнку. Падает (exit≠0) → push не уходит.
💻 ПК🟡 опц.обходим --no-verifyполный юнит-сьют — ВСЕ тесты проекта, не только изменённого (тесты пишешь сам, гоняет cargo test)тайпчек типы сходятся (готовый: компилятор Rust)сборка собирается ли проект целиком (готовый: cargo build)ключевые интеграционные (тесты пишешь сам, cargo test)▰▰▱▱ минутыпоследний локальный рубеж перед тем, как код уйдёт на GitHub и станет общим. Тяжелее pre-commit (весь проект, не только изменённое), но push реже коммита — можно позволить. Быстрее, чем гонять CI на битом коде. Обходим (--no-verify) → удобство, не гарантия (гарантию даёт CI на сервере).
git push 💻 → ☁️код уходит на сервера GitHub · дальше события и проверки уже ТАМ, на чистой машине, обойти нельзя
⑤ свой git-сервер 🚫 НЕ НАШ СЛУЧАЙ — для полноты картины. Это голый git init --bare + SSH на своей машине (git ≠ GitHub!): даёт серверные хуки, но НИ PR, НИ Actions, НИ rulesets. У нас remote = github.com ради ворот. · ⚠️ серверные хуки НЕ обходятся --no-verify — ярлык «обходимы» выше касается только локальных ①–④
pre-receive / update
сервер принял push
Серверные git-хуки на ТВОЁМ git-сервере (не на GitHub). Срабатывают когда сервер получил push, но ещё не записал в refs. Падает (exit≠0) → push отклонён. pre-receive — раз на весь push; update — на каждый реф (ветку ИЛИ тег: пример v*.*.* ниже — это теги).
💻 свой сервер🟡 опц.только push-to-deployзащита ветки — запретить прямой push в main (свой скрипт; на GitHub = branch protection)формат рефов — имена по правилу: feature/*, v*.*.* (свой скрипт)подпись коммитов — пускать только подписанные (свой скрипт)▰▱▱▱ мгновеннотвой аналог branch protection, но на СВОЁМ сервере (если push-to-deploy на свой bare-репо вместо GitHub). Решает на приёме: впустить push в историю сервера или отклонить. На GitHub этих хуков нет — там сервер не твой, роль играет branch protection.

⑥ после push — ядро проверок
on: push
push дошёл до GitHub
НЕ git-хук — триггер в .yml (workflow), пишешь сам. Срабатывает на серверах GitHub: оркестратор читает .yml → раннер (чистая машина) выполняет. Обсервер — сам не блокирует.
☁️ GitHub🔴 ОБЯЗ.минимум для любого проектаполный юнит — ВСЕ тесты проекта (тесты пишешь сам, cargo test)интеграционные — части вместе, реальные БД (тесты сам + готовый Testcontainers)SAST — код на дыры статикой (готовый: Semgrep / CodeQL)SCA — библиотеки на CVE (готовый: cargo-audit)тайпчек + сборка (готовый: компилятор / cargo build)порог покрытия — % кода под тестами (готовый: cargo-llvm-cov)▰▰▰▱ минуты (<10)первая проверка на ЧИСТОЙ машине (раннер с нуля) — ловит «работает только у меня из-за локального хлама», чего pre-push не может. Но сам прогон обходим: ① [skip ci] в сообщении коммита официально пропускает workflow; ② сам .yml лежит В РЕПО — кто пушит (в т.ч. твой LLM-агент!), может его ослабить или удалить. Гарантию даёт связка required check + branch protection: исчезнувший workflow вечно «Pending» → merge заблокирован. Ослабленный ИЗНУТРИ ловится только ревью правок .github/** — root of trust: кто пишет файл-правило, тот и победил.
on: pull_request
PR открыт / обновлён
Триггер в .yml (как on:push), но на событие PR: открыт или обновлён новым пушем. Тоже обсервер, на чистой машине. Контекст — предлагаемое слияние ветки в main.
☁️ GitHub🔴 ОБЯЗ.всё из on:push — полный юнит + интеграционные + SAST + SCA + сборкаконтрактные — границы сервисов/API (тесты сам + готовый Pact)компонентные — UI-компоненты (тесты пишешь сам)дифф покрытия — покрытие именно изменённых строк (cargo-llvm-cov лишь генерит отчёт; сам дифф считает надстройка: Codecov patch / diff-cover)smoke E2E — быстрый прогон критичных флоу (тесты пишешь сам)ревью — человек (место в PR) / Claude (готовая интеграция Action)▰▰▰▱ минутыPR — это предложение влить ветку в main, и здесь стоит merge-гейт. on:pull_request гоняет проверки на ЭТОТ предполагаемый merge + добавляет то, чего нет на push: ревью (человек/Claude) и дифф покрытия. Последний автоматический рубеж перед слиянием в общую ветку.

on: pull_request_review
ревью отправлено
Триггер в .yml. Срабатывает, когда ревьюер ОТПРАВИЛ ревью (approve / request-changes / comment). Реагирует на факт ревью — это не проверка, а зацепка для скрипта.
☁️ GitHub🟡 опц.ревью обяз. для критич. кодасамо ревью — суждение: дизайн, логика, читаемость (человек / Claude — происходит на on:pull_request)реакция на ивент — при аппруве авто-метка, при request-changes оповещение (свой скрипт)ревью ловит то, где тесты бессильны: удачен ли дизайн, читаем ли код, верна ли логика — это человеческое / LLM суждение, не сверка с эталоном. Сам ивент лишь реагирует на отправку ревью (например, метка «одобрено»). Не путать: ревью = ценность, ивент = триггер на его отправку.
branch protection
Merge ИЛИ прямой push в main
НЕ событие и НЕ скрипт — это НАСТРОЙКА репозитория (правило на ветку main). Включаешь галочками в настройках GitHub, не пишешь .yml. Держит ДВЕ двери: кнопку Merge и прямой push мимо PR. Современный вариант той же настройки — rulesets (та же роль, гибче; classic тоже ок).
☁️ GitHub🔴 ОБЯЗ.это и есть принуждениене гонит проверки — ТРЕБУЕТ их. Включаешь галочками (настройка GitHub, не код)зелёные status checks — результаты CI из on:push/PR должны пройтиN аппрувов — нужно ≥N одобрений ревью (соло → 0)+ опц. галочки: линейная история, подписанные коммитыпорог покрытия — НЕ галочка: приходит как сторонний required check (Codecov / свой CI-job, падающий ниже порога)▰▱▱▱ мгновенно (гейтит)ЕДИНСТВЕННОЕ, что делает проверки обязательными. Без него зелёный/красный CI — просто информация: можно слить и красное. Блокирует кнопку Merge, пока условия не сошлись — превращает совет в стену. На своём сервере та же роль у pre-receive/update.
on: merge_group
элемент в merge queue
Триггер в .yml. Срабатывает для каждого элемента очереди слияния. Очередь выстраивает много PR в линию и тестирует каждый в КОМБИНАЦИИ со стоящими впереди, ДО слияния.
☁️ GitHub🟡 опц.только при большом потоке PRфинальный прогон сьюта — те же тесты (юнит/интеграция), но на комбинации «этот PR + стоящие впереди» (тесты пишешь сам, те же что в CI)▰▰▰▱ минутыловит «по отдельности зелёные, вместе ломаются» на уровне НЕСКОЛЬКИХ PR: каждый PR зелёный против СТАРОГО main, но против main+другие-PR его не гоняли. Очередь проверяет эту комбинацию перед автомерджем. (То же, что pre-merge-commit, но на уровне очереди PR.) Соло мерджишь по одному — комбинации нет, не нужно.
⑧ после merge → CD → 🚀 прод
on: push (main)
merge влил → build
Тот же триггер on:push, но отфильтрован на ветку main. Merge в main — это push в main, поэтому срабатывает тут. Начало CD: собрать продукт + просканировать.
☁️ GitHub🔴 ОБЯЗ.сборка + скансборка артефакта — собрать готовый продукт (контейнер/бинарь) ОДИН раз + SBOM (список всех компонентов) (готовый: docker build, SBOM: syft)скан образа — собранный артефакт на CVE (готовый: Trivy)скан лицензий — лицензии зависимостей ок? (готовый: cargo-deny)▰▰▰▱ минутыmerge влил в main → теперь main поедет в прод. Собираешь артефакт ОДИН раз и сканируешь сам собранный продукт на CVE ДО выката. Принцип «build once, deploy many»: тот же артефакт катишь на staging и прод (не пересобираешь на каждом — иначе можешь получить разное).
on: release → staging
выкатка на двойник
Триггер в .yml на событие release (опубликован тег/версия). Берёт готовый артефакт из build, выкатывает на staging. ⚠️ Раскладка «release→staging, кнопка→прод» — ОДИН из вариантов; чаще наоборот: каждый merge в main авто-едет на staging (on:push main), а release/тег — на ПРОД (+ approve через environment).
☁️ GitHub→ 🚀 staging🟡 опц.staging ИЛИ эквивалент (ephemeral / canary)полные интеграционные + контрактные — на прод-подобной среде (тесты пишешь сам + Pact)E2E критичные — весь путь пользователя через запущенный апп (тесты сам + готовый Playwright)DAST — атаки по запущенному приложению (готовый: ZAP, бывш. OWASP ZAP, ныне ZAP by Checkmarx)нагрузочные — грузи до отказа (готовый: k6)chaos — ломай компоненты нарочно (готовый: Toxiproxy)▰▰▰▰ 10+ минутstaging = двойник по КОНФИГУРАЦИИ и версиям, без клиентов (данные и масштаб всегда беднее прода — PII не копируют, нод меньше; потому и существует shift-right). Тут гоняешь ТЯЖЁЛОЕ и РАЗРУШИТЕЛЬНОЕ (нагрузка до отказа, атаки, chaos) — на живом проде это уронило бы клиентов. Ловит средовые баги (ломается только в прод-среде, не локально) + полносистемные + реал-интеграционные. DAST/нагрузка требуют ЗАПУЩЕННЫЙ апп — потому тут, не в CI. Катишь ТОТ ЖЕ артефакт из build.

on: schedule (cron)
ночью по таймеру
Триггер в .yml, но НЕ на git-событие — по ТАЙМЕРУ. cron = синтаксис расписания (мин час день мес день-недели): 0 3 * * * = в 3:00 ежедневно. Единственный, кто срабатывает САМ — без чьего-либо действия вообще (кнопка/коммент/релиз тоже без push, но их жмёт человек). Читается только из main; под нагрузкой GitHub может задержать запуск.
☁️ GitHub🟡 опц.желательно для зрелогополный E2E-регресс — ВСЕ E2E, не только критичные (тесты сам + Playwright)мутационные — качество тестов, критич. модули (готовый: cargo-mutants)нагрузочные / стресс — долгие прогоны под нагрузкой (готовый: k6)фаззинг — мусорный ввод, ищет краши (готовый: cargo-fuzz)полные security-сканы — глубокие SAST/DAST (готовые)▰▰▰▰ часысамое медленное (часы), что не влезает в дневной цикл: повесь на push — CI станет часовым и его начнут обходить. Уводишь в ночь по таймеру, когда никто не ждёт. Не привязано к коду — ловит накопившееся: новые CVE в зависимостях, регрессии, редкие баги от фаззинга.

обязательность — что гейтить, что пропустить

🔴 ОБЯЗ.CI на push/PR (юнит+интеграция+SAST/SCA как required check), branch protection, build+скан, а с клиентами — smoke/health на проде. «Безопасность, что зависит от памяти человека — это не безопасность, а надежда».
🟡 ОПЦ.pre-commit, commit-msg, pre-push (удобно, но обходимо); контрактные (если есть сервисы); мутации (критич. модули); merge_group (большой поток PR); nightly (зрелый проект); ревью (обяз. для критич. кода).
⚪ НЕЧЕГОхозяйственные обсерверы: post-checkout, prepare-commit-msg, post-commit, post-merge, триггеры. Тут нечего проверять — только реакция.

Минимум для соло (твой случай): on:push/PR с юнит-тестами как required check + branch protection. Остальное добавляешь по мере роста — staging/E2E/canary имеют смысл, когда появятся клиенты. ⚠️ Две ловушки: branch protection на ПРИВАТНОМ репо доступна только с Pro-плана (на Free — только публичный репо; наш overlay_script публичный → доступна, см. «блокер снят» ниже); и включи «Do not allow bypass» — по умолчанию админ правила ОБХОДИТ, а соло-админ = ты сам и твой LLM-агент.

тяжесть тестов — staging vs прод (зеркальная логика)

🟢 STAGING — двойник без клиентов
ТЯЖЁЛОЕ и РАЗРУШИТЕЛЬНОЕ: полный E2E, нагрузочные / стресс (грузи до отказа), DAST (атаки по запущенному), chaos (ломай компоненты нарочно). Можно — клиентов нет, ронять не страшно.
🔴 ПРОД — живой трафик
только ЛЁГКОЕ и БЕЗОПАСНОЕ: smoke, health-checks, синтетический мониторинг, canary-анализ. Стресс / атаки / chaos по живым клиентам — нельзя.

Это не одинаковые тесты, а зеркало: на двойнике гоняешь то, что на проде уронило бы клиентов; на проде — только наблюдение и лёгкая проверка живости. Staging — это не «полу-прод», а копия по конфигурации и версиям, изолированная от живых пользователей, чтобы было где гонять разрушительное без риска. Но данные и масштаб у него всегда беднее прода (PII не копируют, машин меньше) — потому часть багов ловится только на живом проде (shift-right).

ЛОКАЛЬНЫЕ ХУКИ — чем управлять и почему фреймворк

у git НЕТ конфига для хуков — вот и вся причина

git умеет РОВНО ОДНО:
   git commit → есть исполняемый файл .git/hooks/pre-commit?
                └ есть → запусти. exit 0 = коммит, exit ≠0 = стоп.
   Больше git не знает НИЧЕГО: ни что внутри, ни какие инструменты нужны.

Сравни с системами, где конфиг ВСТРОЕН:
   Claude Code  события ✅ + конфиг ✅ (.claude/settings.json)  → фреймворк не нужен
   GitHub       события ✅ + конфиг ✅ (.github/workflows/*.yml) → то же
   git локально события ✅ + конфиг ❌                          → доносит фреймворк

Что такое «фреймворк» здесь: программа, которая добавляет git недостающий слой. Ты пишешь .pre-commit-config.yaml (обычный файл в корне, в git), команда pre-commit install один раз генерирует .git/hooks/* со строкой «прочитай конфиг и выполни». Хук есть в обоих случаях, событие то же, проверки те же — меняется только где живёт СПИСОК.

зачем конфиг вместо своего bash-скрипта

ВИДИМОСТЬхук в .git/hooks я меняю — в диффе и PR НЕ видно. Конфиг в корне — видно. Это Э3-урок: правило, живущее вне просматриваемой истории, охраняет само себя
ВЕРСИИrev: v0.16.0 — фреймворк скачает ИМЕННО эту версию в изолированное окружение. Свой скрипт надеется, что «ruff установлен» — какой, неизвестно
ИСТОРИЯ.git/ не версионируется: сломал хук — откатить нечем; склонировал репо — хуков нет, молча
ФИЛЬТРtypes: [python] одной строкой вместо ручного if [[ $file == *.py ]]
МИФ«хуки не работают в worktree» — неверно: проверено, все 4 worktree делят одну .git/hooks (git rev-parse --git-path hooks одинаков) → pre-commit install делается ОДИН раз

ОДИН конфиг для локали и CI — защита от single-source-drift

.pre-commit-config.yaml   ← обычный файл в репо. Едет с push, как код.
     ├─ ЛОКАЛЬНО: git commit → сгенерированный хук → читает ЭТОТ файл
     └─ В CI:     раннер клонировал репо → видит ТОТ ЖЕ файл
                  workflow (~10 строк, пишется ОДИН раз):
                      - run: pre-commit run --all-files   ← «выполни список»
                      + actions/cache на ~/.cache/pre-commit  (бережёт квоту минут)

Добавил проверку → правишь ТОЛЬКО конфиг. Workflow не трогаешь: он не содержит списка.

Куда девают pytest: ОТДЕЛЬНЫМ job'ом в CI, не через конфиг. Граница проходит по природе проверки: pre-commit = быстрые пофайловые (нужен список изменённых файлов), pytest = поведение кода (нужны все файлы + установленный проект). Дублирования при этом нет — список линтеров всё равно в одном файле.

❌ ГЛАВНЫЙ АНТИПАТТЕРН — самый «очевидный» способ, который стабильно разъезжается:
в workflow пишут pip install ruff && ruff check ., при том что ruff уже перечислен в конфиге с rev: v0.16.0. pip притащит САМЫЙ СВЕЖИЙ ruff (релизится почти еженедельно) → локально зелено, в CI красно, причина неочевидна. Это single-source-drift в чистом виде: CI должен ВЫЗЫВАТЬ конфиг, а не повторять его список.

Не подходит нам: pre-commit.ci (облачный сервис) — бесплатен только для публичных репо, приватный личный аккаунт $10/мес. Официальный pre-commit/action жив, но в maintenance-only. Берём голую строку + actions/cache.

⚠️ Ловушка установки: pre-commit install ставит ТОЛЬКО хук pre-commit. Пропишешь stages: [pre-push] — не сработает, пока не выполнишь pre-commit install --hook-type pre-push (или не укажешь default_install_hook_types в конфиге). Тихо, без ошибки.

путь до конфига — кто как доходит до нашего рецепта

① ЛОКАЛЬНЫЙ GIT
git commit
  └─► git ищет ФАЙЛ с именем события: .git/hooks/pre-commit   ← НЕ в репо
        git больше ничего не знает — ни про фреймворк, ни про рецепт
        └─► переходник, 20 строк:
              python -m pre_commit hook-impl --config=.pre-commit-config.yaml
              └─► pre-commit читает .pre-commit-config.yaml   ← НАШ рецепт
                    └─► инструменты из склада ~/.cache/pre-commit
                          └─► гонит по ИЗМЕНЁННЫМ файлам → 0 / не-0

② GITHUB ACTIONS
push / открыт PR
  └─► GitHub читает .github/workflows/ci.yml    ← ЕГО рецепт (on:/branches:/paths:)
        ├─ чистый раннер
        ├─ checkout           → код + тесты + ОБА рецепта
        ├─ pip install .[dev] → появился pytest   ← ручной шов language:system
        ├─ actions/cache      → склад по хешу рецепта
        └─ шаг: pre-commit run --all-files
              └─► pre-commit читает .pre-commit-config.yaml  ← ТОТ ЖЕ рецепт
                    └─► job «lint» зелёный / красный = всего лишь НАДПИСЬ

③ RULESET
нажата кнопка Merge
  └─► GitHub смотрит СВОЮ настройку (в репо её НЕТ — только REST /rulesets)
        └─► сверяет required checks с ИМЕНАМИ job'ов и их статусом
              ↑ имя JOB, а НЕ имя workflow — опечатка = проверка «не пришла»
              └─► все зелёные → merge разрешён
                  красный / отсутствует → КНОПКА ЗАБЛОКИРОВАНА

Склад не возят — его пересоздают. Раннер идёт за инструментами не к тебе, а к первоисточнику, по тем же rev:. actions/cache — это склад самого раннера, отложенный в камеру хранения GitHub; ключ pre-commit|<хеш python>|hashFiles('.pre-commit-config.yaml'). Правишь rev → меняется хеш → ключ другой → склад строится заново. Рецепт определяет склад механически, через хеш — отстать он не может по конструкции.

что из этого следует — порядок ступеней не произволен

①②③ читают НАШ рецепт ──► выдают ВЕРДИКТ
                              │
        ruleset рецепта НЕ читает ──► читает ВЕРДИКТ ②
                                      и превращает надпись в ЗАПРЕТ

1 · Ступень 3 без ступени 2 бессмысленна. CI будет честно краснеть в пустоту: кнопка Merge остаётся живой, пока запрет не выдаст ruleset. Красный чек сам по себе — надпись.

2 · Ruleset слеп к содержанию. Он знает только имя job и его цвет. Переименовал job — проверка «исчезла», кнопка встала намертво. И наоборот: job из одной строки echo ok он пропустит с чистой совестью. Смысл проверки сторожит только ревью.

3 · Настоящая стена одна. Локальный хук снимается --no-verify, CI — «просто не пушить», и оба ставил ты сам. Стена там, где решение принимает не твоя машина — то есть ruleset, и то лишь при пустом bypass list.

4 · Хуками нельзя выстроить всё. Хук — реакция на событие, поэтому он физически не срабатывает, когда события не было. «Тестов не написали вовсе» ловит покрытие как required check (по факту прогона), «прогон вообще не случился» — только dead man's switch: внешний наблюдатель, звонящий на ТИШИНУ.

Полная решётка «событие · матчер · if · сито в скрипте · узел исходов» на все четыре системы (включая Claude-харнесс) — в claude-code-hooks-map, раздел «Четыре системы рядом». Здесь намеренно только конвейерные три, чтобы один факт не жил в двух шпаргалках.

верификаторы — что это за тесты (твой список)
Юнит unit 60–70%
тестирует одну функцию/метод ИЗОЛИРОВАННО (без БД, без сети). Быстро (мс), много. «Работают ли кусочки сами по себе».где: каждый коммит — pre-commit, pre-push, CI
Интеграционные integration 20–30%
проверяют, что разные части работают ВМЕСТЕ — реальная БД, очередь, API (через контейнеры, Testcontainers). Медленнее юнита. «Кусочки стыкуются».где: CI на PR / merge
Контрактные contract / Pact
фиксируют границу между сервисами: потребитель публикует ожидания (что шлёт/ждёт от API), поставщик их выполняет. Для микросервисов/API — ловят «тихие» поломки интерфейса без E2E.где: CI на PR, для каждого нового эндпоинта
Компонентные component
один компонент ЦЕЛИКОМ в изоляции: UI-компонент с шаблоном и событиями без сети — ИЛИ один сервис с замоканными соседями. Быстрее E2E, реалистичнее юнита.где: CI на PR
E2E end-to-end 5–10%
проходит ВЕСЬ путь пользователя через запущенное приложение (логин → заказ → подтверждение). Медленно, хрупко, дорого → только критичные флоу. «Пользователь реально может сделать то, что ты построил».где: smoke на PR, полные на staging + nightly
Smoke дымовые
быстрое подмножество E2E после деплоя — «дым пошёл?»: базовая проверка, что выкаченное вообще живо (главные страницы открываются, API отвечает).где: CI на PR (короткий прогон критичных флоу) и после деплоя на staging/прод
Мутационные mutation / Stryker
проверяют качество твоих ТЕСТОВ, а не код: намеренно ломают код (мутируют — меняют + на −) и смотрят, заметят ли это тесты. Тест прошёл на сломанном коде → тест бесполезный. Медленно и дорого.где: nightly, на критичных модулях
SAST / DAST security
SAST — статика: сканирует исходный код (не запуская) на дыры (инъекции, XSS). DAST — динамика: бьёт по запущенному приложению снаружи (ZAP by Checkmarx, бывш. OWASP ZAP).где: SAST — CI; DAST — staging
SCA скан зависимостей
сканирует сторонние библиотеки на известные дыры (CVE): «используешь lib X v4.2 → у неё CVE → флаг». Rust → cargo-audit.где: CI + build (на коде и на образе)
Нагрузочные / перф load / performance
держит ли система нагрузку — много одновременных запросов, не деградирует ли latency под трафиком.где: staging + nightly
Фаззинг / property fuzz
фаззинг — кормит случайный/мусорный ввод, ища падения и краши. property-based — проверяет свойства на множестве сгенерированных входов (а не на конкретных примерах).где: nightly / CI для критичного
Canary-анализ shift-right
выкат новой версии на малый % реального трафика с отслеживанием метрик (error-rate, latency); растут ошибки → авто-откат. Ловит то, что видно только на живых пользователях.где: прод, при выкатке
Exploratory человек
человек пользуется как пользователь БЕЗ скрипта, пробует странные сценарии, ищет НЕИЗВЕСТНОЕ — то, что никто не догадался автоматизировать. Автотест ловит заданные ожидания; exploratory — неожиданное.где: staging, человеком до релиза
UAT user acceptance человек
заказчик / реальный пользователь судит «ГОДИТСЯ ли для реальной работы» перед запуском. Не «работает ли технически» (это CI), а «то ли это вообще, что нужно».где: staging перед выкатом на прод
Бета beta человек
реальные клиенты раньше всех пользуются продуктом в жизни и шлют обратную связь словами («неудобно», «запутался»). Рядом с canary, но canary — авто-метрики, бета — человеческий фидбэк.где: прод, ограниченному кругу
AI-агентное autonomous ИИ
ДВА разных класса, не путать: ① агентное UI-тестирование — LLM-агент имитирует пользователя, сам исследует пути (exploratory, но автомат); ② детерминированная симуляция (Antithesis) — вся система в детерминированном гипервизоре + fault-injection + фаззинг, быстрее реального времени; пользователя НЕ имитирует, ищет редкие СИСТЕМНЫЕ баги. Оба дополняют, не заменяют человеческое «удобно / то ли это».где: дополнительно к автотестам
ещё миры и техники — что перенять для качества
Ephemeral / Preview мир
временный полный мир на КАЖДЫЙ PR со своим URL: поднимается при открытии PR, сносится при merge. Ревьюер тыкает живую сборку, а не скриншоты. Тренд 2026 — заменяет общий staging для ревью и QA; тяжёлое (нагрузка / DAST / chaos) всё равно требует прод-двойника.соло: избыточно — это лекарство от очередей в командах
Feature flags техника
разделяет деплой и релиз: код физически в проде, но выключен; включаешь по сегментам в рантайме без передеплоя. Kill-switch — мгновенно вырубить сломанное. Unleash, Flagsmithсоло: ДА — kill-switch + катишь незаконченное безопасно
Progressive delivery зонтик
постепенный выкат с мониторингом на каждом шаге: 1% → 5% → 100%, откат при росте ошибок. Объединяет canary + blue-green + флаги. Превращает релиз из события в управляемый процесс.
Blue-green техника
два одинаковых прода (синий / зелёный): новая версия на «зелёном», переключаешь трафик мгновенно, при проблеме — назад на «синий». Ноль простоя, мгновенный откат.соло: можно — ради нулевого даунтайма
Dark launch техника
выкат кода в прод ДО того, как его увидят пользователи (за выключенным флагом). Прогреваешь, тестируешь на реальных данных, потом включаешь.
Testing in production техника
включаешь фичу только для внутренних / QA-аккаунтов в проде — с реальными данными и трафиком, под флагом. То, что staging-двойник не воспроизведёт.
GitOps техника
git — единственный источник правды для состояния инфры / деплоя: меняешь yaml в репо → агент (ArgoCD) приводит прод к описанному. Откат = git revert.соло: тяжеловато, но идея ценная
IaC техника
инфраструктура как код: серверы / окружения описаны в коде (Terraform / OpenTofu), воспроизводимы, под версией. Никаких «настроил руками и забыл».соло: по вкусу, но дисциплинирует
Observability техника
3 столпа: метрики + логи + трейсы с первого дня (OpenTelemetry), не как заплатка после первого инцидента. «Систему, которую не видишь, не можешь чинить».соло: ДА — с самого начала
Chaos engineering техника
намеренно ломаешь компоненты и вносишь задержки (Toxiproxy), чтобы проверить, выживает ли система. «Работает на моём оптоволокне» ≠ «работает в реальных условиях».соло: позже, когда есть что ронять
AI сдвигает CI/CD: скорость → риск принцип
когда код пишет агент, медленный пайплайн больше не блокирует человека (агент не переключает контекст). Приоритет смещается с «сэкономить 10 минут» на снизить риск, что агент выкатит баг — значит можно гонять больше тестов и медленнее, но тщательнее.прямо твой случай с 888 / агентами
варианты: где хранить git — куда пушить
Обычный локальный репо у тебя сейчас
git init на твоём ПК — папка с .git + файлы. НЕ сервер: просто история на диске, извне сюда не пушат.CI/PR/веб: нет · это база, где работаешь
Свой git-сервер (bare) своё
git init --bare на машине с SSH. Голая история без файлов — склад для приёма push. Хуки pre-receive/post-receive → push-to-deploy.ставится: git init --bare + SSH, отдельный софт не нужен · у тебя белый IP — можешь
GitHub облако
github.com, чужие сервера. Actions (CI), PR, branch protection, ревью — всё готовое.ставится: ничего, регистрируешься · дефолт ради готовой инфры
Gitea / GitLab self-hosted
GitHub-подобная платформа на ТВОЁМ сервере: веб-морда, PR, CI. Отдельный софт поверх git.ставится: развернуть софт (Docker / пакет) · когда хочешь GitHub-удобства, но всё своё
GitHub Enterprise Server облако на своём
Сам GitHub на своём железе (для компаний) — «локальный GitHub» в точном смысле. Всё как у GitHub.когда: крупные компании с требованием on-premise
