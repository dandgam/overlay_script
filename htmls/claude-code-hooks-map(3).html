Хуки: две оси, три сита, один узел исходов

Хук — это не событие в нейросети. Это точка в коде обвязки (харнесса), к которой ты прикрепляешь исполнителя. Модель пишет просьбы текстом; руки, цикл и все контрольные точки — у обвязки. Ниже — вся карта этих точек и правила игры на них.

Куда смотреть — четыре маршрута

Запретить действие СутьТочка стоит до действия — исполнения ещё не было, поэтому двойка (или deny) — настоящий блок: действие просто не произойдёт. Единственный маршрут с гарантией. ПримерМодель просит редактирование, а спеки на диске нет → отказ с причиной «сначала создай спеку через скилл». Хоть сто просьб подряд — сто отказов: проверяет скрипт, а не настроение. Смотри2 = БЛОК-точки до действия: PreToolUse, PermissionRequest, UserPromptSubmit · рецепт 1.
Подсказать знание СутьНичего не запрещаем — добавляем модели справку в контекст (впрыск), чтобы она сама пошла правильной дорогой. Уровень промптовый: срабатывает почти всегда, но это не гарантия. ПримерВ сообщении мелькнуло «добавим фичу» → скрипт довесил: «по правилам проекта фича начинается со спеки, скилл такой-то». Или после сжатия контекста впрыснуть ветку и текущую задачу. СмотриЗелёные точки (stdout → контекст): UserPromptSubmit, UserPromptExpansion, SessionStart; на остальных — довесок additionalContext · рецепты 2–3.
Отреагировать на результат СутьТочка стоит после действия — файл уже изменён, команда уже выполнена, отменять нечего. Двойка тут не стоп-кран, а записка с претензией: текст из потока ошибок подкладывается модели как замечание к результату, и она чинит следующим шагом. ПримерПравка прошла → линтер нашёл ошибки → фидбек со списком → модель сама исправляет и проверяет заново. Ты не участвуешь. Смотри2 = ФИДБЕК: PostToolUse, PostToolUseFailure (а PostToolBatch — исключение: умеет остановить весь цикл) · рецепт 4.
Заставить продолжать СутьМодель говорит «я всё» — а скрипт сверяет условие готовности. Не готово → остановка блокируется с причиной «рано, вот что доделать», и модель продолжает работать вместо завершения. ПримерКонец хода → тесты красные → «не заканчивай, чини» с логом падений. Или задачу закрывают без артефакта на диске → закрытие не пускается. СмотриГраницы: Stop, SubagentStop, TaskCompleted, TeammateIdle · рецепт 6. Обязательная страховка от вечной петли — проверка флага stop_hook_active.

Одна картинка на все четыре маршрута — цех: вахтёр до станка может не пустить (запретить) · памятка на стене у входа подсказывает порядок работы (подсказать) · приёмщик после станка брак уже не предотвратит — лишь кладёт рабочему акт, и тот переделывает (отреагировать) · мастер в конце смены не подписывает уход, пока наряд не закрыт (заставить продолжать).

Модель целиком: 2 оси × 3 сита × 1 узел

Ось 1 — Событие (где)

Точка цикла обвязки, к которой прикреплён хук. Точки различаются ритмом — как часто через них идёт поток. Три вложенных масштаба времени, матрёшка (цифры — типичный вечер):

СЕССИЯзапуск → закрытие · ×1
ХОДтвоё сообщение → конец ответа · ×30
ВЫЗОВодна заявка на инструмент · ×300

Границы матрёшек — и есть точки трёх ритмов: сессию открывает и закрывает SessionStart / SessionEnd (старт повторяется на resume и после сжатия); ход — UserPromptSubmit на входе, Stop на выходе; каждый вызов — PreToolUse / PostToolUse вокруг инструмента.

Правило цены: выбор точки = выбор частоты. Тяжёлые проверки — на редкие границы (старт), на частых точках скрипт обязан быть мгновенным: на инструментальной он выполнится сотни раз, и каждый раз заявка ждёт вердикта.

Остальные точки — «по происшествию», без расписания: сжатие, смена папки, жизнь субагента. Всего 30 точек — карта ниже.

Ось 2 — Исполнитель (кто)

Кто придёт работать, когда точка сработала. Оси независимы: точка = «когда», исполнитель = «кто», комбинируются почти свободно — жёсткое исключение одно: SessionStart и Setup принимают только command и mcp_tool (модели на старте ещё нет). Детали по точкам — колонка «Исполнители» в большой таблице.

Разводи два момента: срабатывание (позовут ли) — детерминировано у всех пяти, точка зашита в код обвязки. Вердикт (что скажет) — делит пятёрку на два лагеря:

ВЕРДИКТ ВЫЧИСЛЯЕТ КОД — «калибр»: одинаковый вход → одинаковый ответ command — локальный скрипт; рабочая лошадка, все шлагбаумы http — веб-запрос центральному сервису политики; обрыв канала = пропуск (fail-open) mcp_tool — инструмент подключённого MCP-сервера; «не подключён» = пропуск
ВЕРДИКТ ВЫНОСИТ МОДЕЛЬ — «мастер на глаз»: судит по смыслу, может ошибиться prompt — одноразовый вопрос модели, ответ да/нет («похоже на утечку данных?») agent — мини-агент: сам читает файлы перед ответом; экспериментальный

Правило выбора: начинай с командного; вероятностные — только когда условие невыразимо кодом (смысл, не форма); жёсткую безопасность на них не строить — их ошибка и их отказ открывают дверь, а не запирают.

Сита и узел (когда именно и чем кончилось)

  1. Сито 1 — выбор события (есть всегда);
  2. Сито 2 — матчер в настройке (есть не везде);
  3. Сито 2.5 — поле if (только 5 инструментных точек, best-effort);
  4. Сито 3 — условие в самом скрипте (есть всегда).

Узел исходов: 0 молча · 0 + вывод · 0 + JSON-резолюция · 2 (блок) · прочее (дырка).

Где объявлять: пользовательские / проектные / локальные настройки, управляемая политика, плагин, а также фронтматтер скилла или агента — тогда хук живёт только пока компонент активен (флаг once — раз за сессию, работает только в скиллах).

Как выбрать исполнителя — цепочка вопросов (иди сверху вниз, первый «да» решает):
  1. Точка — SessionStart или Setup? → command. Формально можно и mcp_tool, но сервер на старте обычно ещё не подключён — жди ошибку «not connected» на первом запуске.
  2. Нужно вернуть путь (WorktreeCreate)? → command (путь в stdout) или http (worktreePath). Вероятностные путь отдать не умеют.
  3. Это шлагбаум безопасности, который обязан сработать всегда? → command. Он единственный блокирует детерминированно и без сети. http и mcp_tool при обрыве, таймауте или «не подключён» пропускают действие (fail-open); prompt/agent могут ошибиться в обе стороны.
  4. Условие выразимо кодом (имя инструмента, путь, регэксп, наличие файла, код выхода теста)? → command. Быстро, бесплатно, воспроизводимо.
  5. Условие смысловое («похоже на утечку секрета?», «задача реально доделана?») → prompt; если для вердикта надо самому заглянуть в файлы → agent. Обоим место на редких границах (Stop, SubagentStop, TaskCompleted, PermissionRequest), а не на частых точках: медленно, платно и вероятностно.
  6. Единая политика на команду / телеметрия в центр? → http. Логика уже живёт в MCP-сервере? → mcp_tool.

Помни: на одну точку можно повесить несколько исполнителей разных типов — совпавшие стартуют параллельно (например, командный шлагбаум + http-телеметрия на одном PreToolUse). Командные хуки дополнительно умеют async: true — фоновый запуск, не задерживающий цикл (логи, бэкапы, уведомления), и asyncRewake — фон, который при двойке будит модель системным напоминанием. И за пределами настроек: в Agent SDK те же события ловятся колбэками прямо в коде приложения (TypeScript/Python) — шестой «исполнитель», но живёт он в SDK-приложении, а не в settings.json.

Три сита: воронка «когда именно вмешиваться»

Сито 1 — событие

Есть всегда: хук существует только на своей точке. Выбор точки = выбор момента и полномочий (см. цвет двойки).

Сито 2 — матчер

Есть не везде. Без матчера (срабатывают на каждое вхождение): UserPromptSubmit, PostToolBatch, Stop, TeammateIdle, TaskCreated, TaskCompleted, WorktreeCreate, WorktreeRemove, MessageDisplay, CwdChanged — поле матчера там молча игнорируется.

Синтаксис: пусто / * = все; только буквы-цифры-дефис-подчёркивание с разделителями | или запятой = точное имя или список (Edit|Write); любой другой символ = JS-регулярка без якорей — Edit.* ловит и NotebookEdit, якори как ^Edit$. Регистрозависимо: bash ≠ Bash. MCP-инструменты: mcp__сервер__инструмент, весь сервер — mcp__сервер__.* (хвост .* обязателен).

Сито 2.5 — поле if

Только у пяти инструментных точек. Одно правило в синтаксисе разрешений: Bash(git *), Edit(*.ts) — сверяет имя вместе с аргументами, экономит запуск процесса. Комбинировать условия нельзя — на каждое своё обработчик. Осторожно: на любой не-инструментной точке хук с полем if вообще никогда не запускается. Best-effort и fail-open: составные команды, цепочки и подстановки $( ) могут не совпасть с правилом — тогда скрипт вообще не позовут и заявка пройдёт без проверки. Поэтому «если» — оптимизация запусков, а жёсткий allow/deny — только системой разрешений.

Сито 3 — логика скрипта

Есть всегда. Скрипту доступны: весь текст сообщения (prompt) или параметры инструмента (tool_input), диск, история диалога по transcript_path, режим разрешений, окружение. Не совпало — молчаливый ноль за миллисекунды. Правило: срабатывание сужают сита 1–2, вмешательство решает сито 3.

JSON-рычаги: универсальный конверт и правила довеска

Рычаги каждой точки слиты в большую таблицу (колонка «Рычаги при нуле» + их живые сценарии в «Реальном применении рычагов»). Здесь — только то, что общее для всех точек.

Универсальный конверт (любая точка)

continue:false + stopReason — заглушить всё немедленно (сильнее любых decision; stopReason видишь только ты); systemMessage — предупреждение тебе на экран; suppressOutput — спрятать stdout хука из ленты; terminalSequence — системное уведомление / заголовок окна / звонок (замена недоступному /dev/tty).

Оговорки: у StopFailure игнорируется вообще всё; у TaskCreated / TaskCompleted / TeammateIdle конверт — единственный JSON-способ остановки (остальное — двойкой).

Довесок additionalContext

Строка впрыскивается как системное напоминание в месте срабатывания (у старт-точек — перед первым промптом; у инструментных — рядом с результатом; у Stop — в конец хода). Лимит 10 000 знаков (сверх — уходит в файл). Формулируй фактами, не приказами «свыше»: командный тон ловит защита от инъекций и выносит текст тебе на обозрение. При --resume сохранённые довески проигрываются заново — таймстампы устаревают; SessionStart на резюме перезапускается и может освежить.

Переписывание вместо запрета: исходящее к инструментам правь через updatedInput (PreToolUse), входящее от них — через updatedToolOutput (PostToolUse). Текст твоего промпта переписать нельзя — только довесить. И два языка на хук: выбрал двойку — весь напечатанный JSON выбрасывается.

Рецепты: точка · сито · исполнитель · исход

1 · Шлагбаум «сначала спека» (block_until)

PreToolUse · матчер Edit|Write · command · deny / exit 2

Скрипт: спека на диске есть? Нет → deny с причиной «создай спеку через скилл X». Модель может упрямиться сколько угодно — проверка выполняется на каждую просьбу. Уровень по манифесту: physical-hook.

2 · Детектор триггеров на входе

UserPromptSubmit · сито 3: ключевые слова · command · 0 + довесок

Regex по закрытому списку («хочу внедрить», «добавим фичу») → проверил диск → впрыск «по правилам проекта начни со спеки, скилл такой-то». Промптовый уровень — работает почти всегда; гарантию даёт пара с рецептом 1.

3 · Память, пережившая сжатие

SessionStart · матчер compact · command · 0 + stdout

После каждой компакции печатает выжимку контекста (ветка, задача, запреты) — она входит в свежий контекст первой.

4 · Автолинт с возвратом ошибок

PostToolUse · матчер Edit|Write · command · decision:block

Прогнал линтер по правленому файлу; есть ошибки → block с их списком — модель читает и чинит сама, без твоего участия.

5 · Секреты под замком

Permissions (deny-правила) + PreToolUse как второй эшелон

Жёсткий запрет чтения секрет-файлов — правилами разрешений: if у хуков best-effort и fails open, а файлы через @ вообще минуют PreToolUse. Хук — дополнительная сетка, не единственная.

6 · Не останавливаться до зелёных тестов

Stop · command · decision:block + reason

На конце хода гоняет тесты; красные → block с логом падений. Обязательно: если stop_hook_active уже истина — выйти нулём, иначе вечная петля.

7 · Свои worktree для воркеров

WorktreeCreate · command · stdout = путь

Заменяет штатное создание копий своей логикой (нейминг, диск, квоты) — точка стыковки с оркестратором параллельных воркеров. Помни: тут любой ненулевой код срывает создание.

Подводные камни

Единица не блокирует

Полисный хук обязан выходить двойкой. Единица = «hook error», действие проходит. Единственное исключение — WorktreeCreate.

Двойка глотает JSON

Резолюции разбираются только при нуле. Напечатал decision:block и вышел двойкой — JSON выброшен. Один хук — один язык.

Мусор в stdout ломает JSON

Приветствия шелл-профиля и echo-отладка попадают в stdout и рушат разбор резолюции. Отладку — в stderr или файл.

Матчер: регистр и якоря

bash ≠ Bash; регулярки без якорей (Edit.* ловит NotebookEdit). Точное имя — точными символами или ^…$.

Таймауты входной таможни

UserPromptSubmit ждут максимум 30 с; по таймауту хук снимается, довесок отбрасывается, промпт уходит «голым». MessageDisplay — 10 с.

if — best-effort

Сито 2.5 экономит запуски, но fails open на подкомандах и $( ). Жёсткий allow/deny — только системой разрешений.

Дыры вокруг PreToolUse

Файлы через @ в промпте читаются без вызова инструмента; прямой /скилл минует инструмент Skill (лови на UserPromptExpansion); PermissionRequest не срабатывает в headless.

Петля на границе хода

Stop-хук, который всегда блокирует, зацикливает разговор. Проверяй stop_hook_active и давай выходное условие.

Параллельные переписчики

Несколько PreToolUse одновременно правят updatedInput одного вызова — победит закончивший последним. Один переписчик на инструмент.

Довесок — фактами

Текст «системным приказом» триггерит защиту от инъекций: его вынесут тебе на экран вместо исполнения. Пиши справочно: «цель деплоя — прод».

Резюме проигрывает старое

При --resume сохранённые довески повторяются, хуки за прошлые ходы не перезапускаются — таймстампы и SHA устаревают. Освежай в SessionStart (source=resume).

Версии плывут

API хуков заметно меняется в линейке 2.1.x (новые точки, поля, семантика матчеров). Сверяй на своей версии: команда /hooks и официальный справочник.

Пять слоёв хука — анатомия целиком

Всё, что разобрано выше, складывается в одну конструкцию. Читается сверху вниз: каждая заявка агента проходит слои по порядку, и на любом может остановиться.

① КОНФИГ            .claude/settings.json — список хуков

                      (у git такого файла НЕТ вообще, у GitHub Actions иерархии нет)

Сита сужают поток, рычаг — язык вердикта. Сита 1-2 живут в settings.json и ничего не стоят: не совпало — процесс не запущен. Сито 3 живёт в коде стража, стоит запуска, зато видит любое поле заявки. Путать сито с рычагом — частая ошибка: первое отвечает «кого судить», второй — «что сказать тому, кого судим».

Четыре системы рядом: git · GitHub Actions · ruleset · харнесс

Одна и та же конструкция «событие → фильтр → исполнитель → ответ» реализована в четырёх местах с разной зрелостью. Модель одна — понял одну, читаешь все четыре. Четвёртая, ruleset, выпадает из ряда дважды: её рецепт единственный не лежит в репозитории, и она единственная реально запрещает операцию.

Форматтер — родня updatedInput, и опаснее его. Он не блокирует, а молча переписывает файл на диске и возвращает не-ноль. Отличие от харнесса: подменённый результат не уезжает в операцию — он лежит в рабочей копии и ждёт git add. Опасность реализуется ровно в тот момент, когда ты добавляешь правки не глядя: приняты изменения, которых ты не читал.

Путь до конфига: кто как доходит до нашего рецепта

① ХАРНЕСС
модель попросила Write
   └─► харнесс читает settings.json (user ~/.claude → project .claude; project сильнее)
          сито 1 = PreToolUse · сито 2 = matcher Write|Edit
          └─► запускает исполнителя → сито 3 внутри скрипта → вердикт

② ЛОКАЛЬНЫЙ GIT
git commit
   └─► git ищет ФАЙЛ с именем события: .git/hooks/pre-commit     ← НЕ в репо
          git больше ничего не знает — ни про фреймворк, ни про рецепт
          └─► переходник, 20 строк:
                 python -m pre_commit hook-impl --config=.pre-commit-config.yaml
                 └─► pre-commit читает .pre-commit-config.yaml    ← НАШ рецепт
                        └─► берёт инструменты из склада ~/.cache/pre-commit
                               └─► гонит по ИЗМЕНЁННЫМ файлам → 0 / не-0

③ GITHUB ACTIONS
push / открыт PR
   └─► GitHub читает .github/workflows/ci.yml        ← ЕГО рецепт, сита on:/branches:/paths:
          ├─ поднимает чистый раннер
          ├─ checkout           → приехали код + тесты + ОБА рецепта
          ├─ pip install .[dev] → появился pytest    ← ручной шов language:system
          ├─ actions/cache      → склад по хешу рецепта
          └─ шаг: pre-commit run --all-files
                 └─► pre-commit читает .pre-commit-config.yaml   ← НАШ рецепт, ТОТ ЖЕ
                        └─► job «lint» стал зелёным / красным  = всего лишь НАДПИСЬ

④ RULESET
нажата кнопка Merge
   └─► GitHub смотрит СВОЮ настройку (в репо её нет — читается через REST /rulesets)
          сито 1 = попытка merge · сито 2 = ветка main
          └─► сверяет required checks с ИМЕНАМИ job'ов и их статусом
                 ↑ имя JOB, а НЕ имя workflow — опечатка = проверка «не пришла»
                 └─► все зелёные → merge разрешён
                     красный / отсутствует → КНОПКА ЗАБЛОКИРОВАНА
Читается одним взглядом: ①②③ читают наш рецепт и выдают вердикт — ④ рецепта не читает вовсе, он читает вердикт ③ и превращает надпись в запрет. Отсюда правило лестницы: CI без ruleset краснеет в пустоту. И отсюда же — где настоящая стена: ①②③ снимаются одним движением того, кто их поставил (--no-verify, «не пушить»), ④ стоит там, где решение принимает не твоя машина.
Ruleset слеп к содержанию. Ему всё равно, что именно проверял job — он знает имя и цвет. Практические следствия: переименовал job — проверка «исчезла», кнопка встала намертво; и наоборот, job может быть пустышкой из одной строки echo ok — ruleset пропустит с чистой совестью. Смысл проверки сторожит только ревью.
git (2005)      событие + «запусти файл»                      ПРИМИТИВ
                └─ фреймворк pre-commit доносит: конфиг · версии · изоляцию

GitHub Actions  событие + конфиг + раннер + marketplace       ФРЕЙМВОРК
                └─ но исполнитель один, ответ бинарный

Claude Code     событие + конфиг + иерархия + 5 исполнителей
                + богатый язык ответа + подмена заявки        ФРЕЙМВОРК+
Почему у харнесса пять исполнителей, а у остальных один. git и CI решают МЕХАНИЧЕСКИЕ вопросы («линтер чист? тесты зелёные?») — там достаточно скрипта. Харнесс перехватывает ДЕЙСТВИЯ АГЕНТА, где вопрос бывает смысловым: «опасно ли это по смыслу?». Механику судит код (command), смысл — только модель (prompt/agent). Отсюда и разнообразие.
Три вещи, которых нет больше нигде: ① пять типов исполнителя · ② updatedInput — тихая подмена заявки: при deny модель знает, что её остановили, при подмене думает, что победила · ③ иерархия настроек с precedence (глобальный конфиг и конфиг папки работают одновременно, папка запуска решает).

Мини-словарь

точка / событие
фиксированное место в цикле обвязки, где может запуститься хук; ось 1.
исполнитель
что именно запускается в точке: скрипт, веб-запрос, MCP-инструмент, вопрос модели, мини-агент; ось 2.
матчер (сито 2)
фильтр в настройке: по имени инструмента, источнику старта, типу агента и т.п.
бланк
служебный JSON о происшествии, который обвязка подаёт хуку на вход (stdin / тело POST).
резолюция
структурный JSON-ответ хука при нуле: блок, allow/deny, довесок, переписка аргументов.
двойка / дырка
код выхода 2 — блокирующий сигнал; любой другой ненулевой — неблокирующая ошибка, действие проходит.
впрыск / довесок
текст от хука, добавленный в контекст модели: stdout на зелёных точках или additionalContext где угодно.
шлагбаум (block_until)
блокировка инструментов, пока на диске нет артефакта, который производит только нужный скилл.
витрина
всегда загруженные шапки скиллов (имя+описание), по которым модель выбирает скилл — вероятностно; хуки к ней не относятся.
