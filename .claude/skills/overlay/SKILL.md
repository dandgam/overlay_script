# overlay

Управление `tools/overlay_sync.py` через меню в чате. Каталог → выбор словами → сборка команды → вызов через `Bash` → пересказ результата простым русским. Пользователь **ничего не печатает в терминале** — ведущий Claude.

**Все надписи на русском.** Python CLI — стабильный источник правды; skill это только UI-слой. Не дублировать логику CLI — только собирать команду и звать `Bash`.

## ⚠️ Как вызывать CLI

В системном PATH скрипта нет. Всегда полный префикс (cwd роли неважна — пути в скрипте абсолютные):

```
/home/server/bmad-orchestrator/.venv/bin/python /home/server/bmad-orchestrator/tools/overlay_sync.py
```

**Жёсткие правила вызова (легко ошибиться руками — потому это и делает skill):**
- **Глобальные флаги идут ДО подкоманды.** Всегда подставляй `--exempt /home/server/.claude/bmad-overlays/exempt.yaml`. Дефолты канона/проектов/vault менять не нужно (odyssey · odyssey,legal,pcb,Antares · `~/.claude/bmad-overlays`).
- Подкоманда и её флаги (`--apply`, `--target`, …) идут ПОСЛЕ.
- `init-project` / `post-upgrade` требуют `--target <имя-или-путь>` — спроси, если не назван.
- При записи добавляй `--stamp "$(date -u +%Y-%m-%dT%H:%M:%SZ)"` (имя папки бэкапа).
- Для чтения используй `--json` где возможно (`check`, `census`, `revalidate`, `menu`) — парсь и пересказывай, не вываливай сырой вывод.

## Что делать при вызове

1. **Первое действие — взять каталог из скрипта.** Запусти `… overlay_sync.py --json menu` через `Bash` и читай список операций ОТТУДА. **Не хардкодь список команд в этом файле** — единый источник = скрипт, иначе drift.
2. **Skip-menu.** Если в сообщении явный intent (см. «Триггеры») — пропусти меню, сразу собирай команду.
3. **Иначе покажи меню** — дружелюбный нумерованный список по-русски из каталога: номер · название · пометка `read-only`/`ПИШЕТ` · что делает · (нужен `--target` где есть). Пользователь выбирает словами или номером.
4. **Собери команду** по правилам выше. Покажи её пользователю перед запуском.
5. **Защита записи (ОБЯЗАТЕЛЬНО, owner выбрал «план → спросить → запись»):** для любой команды с пометкой `ПИШЕТ` (`propagate`, `capture`, `init-project`, `post-upgrade`):
   - сначала **dry-run** (тот же вызов БЕЗ `--apply`);
   - пересказать план простым русским: что и куда изменится;
   - запросить явное подтверждение («применить? да/нет»);
   - только после «да» — повтор с `--apply --stamp …`.
   Никогда не давай `--apply` сразу.
6. **Запусти** read-only / подтверждённую запись через `Bash` (foreground), разбери stdout.
7. **Пересказ результата:** переведи в дружелюбный русский (tutor-стиль) и **явно назови смысл exit-кода** (значения — в поле `exits` каталога: 0 ок · 1 предупреждения · 2 ошибки · 3 откат после revalidate · 6 конфликт, дерево/vault не тронуты).

## Карта операций (берётся из `menu`, здесь — для маршрутизации)

| Выбор / intent | Команда | Тип |
|---|---|---|
| «проверь», «что с оверлеями», «расхождения» | `check` (с `--json`) | read-only |
| «перепись форков», «сколько форков» | `census` | read-only |
| «разлей», «синкни канон по проектам» | `propagate` → dry-run → `--apply` | ПИШЕТ |
| «перепроверь сходимость» | `revalidate` | read-only |
| «захвати в vault», «сними overlays» | `capture` → dry-run → `--apply` | ПИШЕТ + commit vault |
| «разверни в проект X», «поставь overlays в X» | `init-project --target X` → dry-run → `--apply` | ПИШЕТ |
| «переналожи форки после апгрейда» | `post-upgrade --target X` → dry-run → `--apply` | ПИШЕТ |

## Чего НЕ делать

- Не давать `--apply` без dry-run + подтверждения.
- Не ставить глобальные флаги после подкоманды (сломается парсинг).
- Не хардкодить список команд — читать из `--json menu`.
- Не предлагать `git commit` / `git push` в целевых проектах: `propagate`/`init-project` пишут файлы, но НЕ коммитят — коммитит owner в своём репо. (`capture --apply` сам коммитит в vault — это штатное поведение скрипта, выполняй после подтверждения.)
- Никогда `--no-verify`, `git reset --hard`, force-push.
